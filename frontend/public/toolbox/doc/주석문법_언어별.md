# 언어별 주석 문법 — 주석 삭제 기능의 근거

`tools/dev_tools.html` 「화면 표시기」의 **주석 삭제** 버튼이 언어별로 무엇을 주석으로 보고 무엇을 남기는지에 대한 판단 근거.
스캐너 규칙을 바꾸기 전에 이 문서를 먼저 본다.

근거는 세 등급으로 나눠 적는다.

| 등급 | 뜻 |
|---|---|
| **문서** | 벤더 공식 문서 인용. 출처 파일 경로를 같이 적는다 |
| **실측** | 실제로 실행해 확인. 수단과 날짜를 같이 적는다 |
| **미확인** | 근거 없이 가정한 것. 어떻게 가정했는지 적는다 |

## 2. SQL — 힌트를 지우면 실행계획이 바뀐다

**문서** — `db_docs/Tibero_SQL참조안내서/ch_sql_elements.html` 2.8절

```
(DELETE|INSERT|SELECT|UPDATE) /*+ hint [hint] ... */
(DELETE|INSERT|SELECT|UPDATE) --+ hint [hint] ...
```

> '+' 기호는 반드시 주석 구분자('/*' 또는 '--') 바로 뒤에 공백 없이 붙여 써야 한다.
> 힌트와 '+' 기호 사이에 공백은 있어도 되고, 없어도 된다.
> 문법에 맞지 않는 힌트는 주석으로 취급되며, 에러는 발생하지 않는다.

**`--+` 형태의 줄 힌트가 있다.** 줄 주석 `--` 를 무조건 지우면 이 힌트가 같이 날아간다.
화면 표시용으로만 쓰면 티가 안 나지만, 삭제 결과를 복사해 옮기면 실행계획이 바뀐 SQL이 된다.

보존 판정은 구분자 바로 뒤 `+` 하나만 본다.

```js
var CMT_HINTS = [/^\/\*\+/, /^--\+/, /^\/\*\s*<OPTGUIDELINES>/i];
var CMT_EXEC  = [/^\/\*M?!/];
```

### DB별 주석형 힌트·실행 주석

| DB | 모양 | 근거 |
|---|---|---|
| Oracle · Tibero | `/*+ … */` · `--+ …` | **문서** — 위 Tibero 2.8절 |
| MySQL | 옵티마이저 힌트 `/*+ … */`, 버전 실행 주석 `/*!80031 … */` | **문서** — dev.mysql.com refman 8.0 「Comments」: 「Hint comments include a `+` character following the `/*` comment opening sequence」, 「If you add a version number after the `!` character, the syntax within the comment is executed only if …」 |
| MariaDB | `/*! … */` · `/*!##### … */` · `/*M! … */` · `/*M!###### … */` | **문서** — mariadb.com/kb 「Comment Syntax」 |
| CUBRID | `/*+ hint */` · `--+ hint` · `//+ hint` | **문서** — cubrid.org manual 11.2 「tuning」: 「there are three styles」. `//` 는 SQL 규칙에서 주석으로 안 보므로 `//+` 는 원래 남는다 |
| Altibase | `/*+ … */` (SELECT 바로 뒤) | **문서** — ALTIBASE/Documents 7.1 「Performance Tuning Guide」 예제 |
| DB2 | 문장 끝 `/* <OPTGUIDELINES> … </OPTGUIDELINES> */` | **문서** — IBM Db2 11.5 「Embedded optimization guidelines」: 「The embedded optimization guideline must be provided after the SQL portion of the statement」 |
| SQL Server | 주석형 힌트 없음. 조인·쿼리(`OPTION`)·테이블(`WITH`) 힌트는 키워드다 | **문서** — learn.microsoft.com 「Hints (Transact-SQL)」 |
| PostgreSQL pg_hint_plan | `/*+ … */` | **미확인** — 확장 문서를 안 열었다. 모양이 같아서 규칙상 남는다 |

- **힌트**(`CMT_HINTS`)는 체크박스를 켜면 지운다. **실행 주석**(`/*!` `/*M!`)은 힌트가 아니라 실행되는 코드라 체크박스와 상관없이 남긴다.
- Oracle 규칙도 `/*!` 를 남긴다. Oracle 에선 그냥 주석이라 남겨도 해가 없다.
  반면 MySQL 덤프를 Oracle 로 골랐을 때 지우면 `SET NAMES` 같은 실행 코드가 사라진다.
- Java·JS·JSX·CSS·LESS 규칙도 `/*+` 를 남긴다. **실측** 2026-09-26 — SQL*Plus 스크립트가 `VAR x NUMBER` 로 JS, `REM` 으로 배치로 오판되면서
  힌트 46건이 일반 블록 주석으로 지워졌다. 이 언어들에서 `/*+` 는 거의 안 나오는 모양이라 남겨도 손해가 없다.
- 결과 문구에 「힌트 n개 남김」·「힌트 n개 삭제」·「실행 주석(/*! */) n개 남김」을 붙인다.

### Oracle 고정 계획(SQL Plan Baseline)과 주석

**문서** — docs.oracle.com 19c 「Overview of SQL Plan Management」: 「A SQL signature is a numeric hash value computed using a SQL statement text that has been normalized for case insensitivity and white space.」

**미확인** — 정규화에 주석 제거가 들어가는지는 문서에 없다. 들어가지 않는다면 주석을 지운 SQL 은 서명이 달라져 붙어 있던 기준 계획을 못 찾는다.
확인 전까지 화면 경고는 넣지 않았다.

힌트 이름이 유효한지는 검사하지 않는다. 틀린 힌트도 Tibero가 주석으로 취급하니,
모양만 보고 남기는 쪽이 안전 방향이다. 위치 조건(`SELECT` 절 바로 뒤)도 보지 않는다 —
서브쿼리·인라인뷰마다 위치를 따지면 스캐너가 파서가 돼야 한다.

기본값은 **보존**. 사이드바 `실행계획 힌트도 삭제 (/*+ */ · --+)` 체크박스를 켜야 지워진다.

### 문자열 이스케이프

**문서** — 같은 파일 2.3.1절

> 문자열 리터럴 안에 작은따옴표를 표현하려면 작은따옴표를 두 번 연속해서 사용해야 한다.
> 문자열 리터럴 안에 작은따옴표를 일반 문자와 같이 취급하려면 q string을 사용하면 된다.
> `q'[…]'` `q'"…"'` `q'|…|'` `q'$…$'`

백슬래시 이스케이프가 아니다. `'It''s'` 는 한 덩어리 문자열이다.
q-quote 구분자는 괄호류(`[ ]` `( )` `{ }` `< >`)면 짝으로 닫고, 그 외 문자는 같은 문자로 닫는다.

### `#` 은 Oracle · Tibero 주석이 아니다

MySQL 전용이다. SQL 프로파일에 `#` 을 넣으면 `SELECT '#1'` 이나 컬럼명 `EMP#` 이 잘린다.
`#` 은 MySQL·셸·YAML·프로퍼티 프로파일에만 둔다.

## 3. XML — 브라우저 파서에 물어본 결과

**실측** — 2026-09-02, Puppeteer 25.8.0 + Chrome `DOMParser('application/xml')`

| 입력 | 파싱 결과 | 스캐너 규칙 |
|---|---|---|
| `<r><!-- a -- b --></r>` | ERR | 주석 안 `--` 는 규격 위반. 관대하게 첫 `-->` 에서 끊는다 |
| `<r><!-- a <!-- b --> c --></r>` | ERR | 중첩 없음 확정 |
| `<r><![CDATA[ <!-- x --> ]]></r>` | OK | CDATA 안은 주석이 아니다. 통째로 남긴다 |
| `<r a="&lt;!--"/>` | OK | 속성값 안은 주석이 아니다. 단 XML은 속성값에 날 `<` 를 못 넣어 실제로는 이 형태로만 나온다 |
| `<r><!-- a ---></r>` | ERR | `--->` 로 끝낼 수 없다 |

XML은 줄 주석이 없다. `<!-- -->` 하나뿐이다.

## 4. JS — `/` 가 정규식인지 나눗셈인지

**실측** — 2026-09-02, Node 22.13.0 `vm.runInNewContext`. 6건 전부 예상과 일치.

| 소스 | 결과 | 뜻 |
|---|---|---|
| `var a=6,b=3,c=2; a / b / c` | `1` | 식별자 뒤 → 나눗셈 두 번 |
| `var x="//"; x.length` | `2` | 문자열 안은 주석이 아니다 |
| `"a//b".replace(/[/]{2}/g,"-")` | `a-b` | `(` 뒤 → 정규식 |
| `(function(){return 1})/1/1` | `NaN` | `)` 뒤 → 나눗셈 |
| `` var t=`x${ 1/*c*/+1 }y`; t `` | `x2y` | 템플릿 `${}` 안은 다시 코드 |
| `typeof /re/` | `object` | 키워드 뒤 → 정규식 |

판정 규칙 — `/` 직전의 공백 아닌 마지막 토큰을 본다.

- `)` `]` 또는 식별자·숫자로 끝남 → **나눗셈**. 단 그 식별자가 키워드면 정규식
- `++` `--` 로 끝남 → 나눗셈 (후위 증감 뒤)
- 그 외(`(` `,` `=` `:` `[` `!` `&` `|` `?` `{` `}` `;` 연산자, 또는 입력 처음) → **정규식**
- 정규식으로 보는 키워드 — `return typeof case in of new delete do else instanceof void throw yield await`

## 5. Java — 텍스트블록과 블록 주석 중첩

**실측** — 2026-09-02, JDK 25.0.1 실제 컴파일·실행

```java
String tb = """
    SELECT * FROM T   -- 텍스트블록 안. 주석 아님
    /* 이것도 아님 */""";
/* 블록 /* 중첩 안 됨 */
char sl = '/';
```

- 텍스트블록 안의 `--` 와 `/* */` 는 원문 그대로 남는다 (길이 48, 첫 줄 무손상)
- 블록 주석은 중첩되지 않는다. 위 코드가 컴파일된다 = 첫 `*/` 에서 끝난다
- `'/'` 문자 리터럴 정상

텍스트블록은 `"""` 를 여닫는 문자열 구분자로 등록해 통째로 통과시킨다.
일반 `"` 문자열보다 **먼저** 검사해야 한다. 안 그러면 `"""` 를 빈 문자열 `""` + `"` 로 읽는다.

## 6. JSP — 세 층이 겹친다

리전을 먼저 자르고, 조각마다 다른 규칙을 적용한다.

| 리전 | 처리 |
|---|---|
| `<%-- … --%>` | 삭제 (JSP 주석) |
| `<!-- … -->` | 삭제 (HTML 주석) |
| `<%@ … %>` | 보존 (지시자. 주석이 아니다) |
| `<% … %>` `<%! … %>` `<%= … %>` | 안쪽에 Java 규칙 적용 |
| `<script> … </script>` | 안쪽에 JS 규칙 적용 |
| `<style> … </style>` | 안쪽에 CSS 규칙 적용 |
| 그 밖의 템플릿 텍스트 | 보존. **여기 있는 `//` 는 주석이 아니다** |

**미확인** — `<%-- --%>` 의 중첩 허용 여부. 로컬에 JSP 엔진이 없어 실행으로 확인 못 했다.
중첩 불가로 가정하고 첫 `--%>` 에서 끊는다. XML 주석과 같은 성질이라는 판단이다.

**미확인** — 스크립틀릿 안 Java 문자열에 `%>` 가 들어간 경우 (`out.print("%>")`).
리전 분리는 `%>` 를 문자열 안까지 따지지 않고 먼저 나오는 것을 끝으로 본다.
JSP 규격이 이 경우 `%\>` 로 쓰라고 요구하므로 실코드에서는 드물다고 보고 넘긴다.

## 7. MyBatis XML — XML 껍질 + SQL 알맹이

같은 파일에 XML 주석과 SQL 주석이 같이 있다. 리전으로 나눈다.

| 리전 | 처리 |
|---|---|
| `<!-- … -->` | 삭제 |
| `<![CDATA[ … ]]>` | 껍질은 남기고 **안쪽에 SQL 규칙 적용**. `<` 연산자 때문에 SQL이 여기 들어간다 |
| 태그 `<select id="…" …>` | 보존. 속성값 안은 건드리지 않는다 (`<if test="a != null">` 는 OGNL) |
| 태그 사이 텍스트 | SQL 규칙 적용 |

XML 프로파일과 갈리는 지점은 텍스트 노드와 CDATA다.
일반 XML은 텍스트에 SQL 규칙을 안 걸어서 `--` 를 그대로 둔다.

## 8. JSX · TSX — 태그 사이 텍스트는 코드가 아니다

**실측** — 2026-09-02, `C:/workspace/portfolio` 의 Next.js `.tsx` 13개.

JSX 를 JS 규칙으로 훑으면 **텍스트 노드가 잘린다.** 실제로 잘렸다.

```
입력   <p>경로는 // 로 구분한다</p>
출력   <p>경로는                     ← </p> 까지 통째로 사라짐
```

`href="//cdn.x/a"` 는 문자열이라 살아남는다. 문제는 **태그 사이 텍스트**다.
JS 문법으로 보면 거기도 코드 자리라 `//` 가 줄 주석이 된다.

그래서 `jsx` 프로파일을 따로 뒀다. `js` 프로파일은 손대지 않았다 — 평범한 JS 에 JSX 스캔을 걸면
`a < b` 같은 비교 연산자를 여는 태그로 오인할 여지만 생긴다.

### 어디서부터 JSX 로 볼 것인가

`<` 가 **식이 올 수 있는 자리**에 있고 다음 글자가 영문자·`_`·`$`·`>` 이면 JSX 원소로 본다.
판정은 정규식 리터럴과 **같은 함수**(`cmtRegexOk`)를 쓴다 — `/` 가 정규식인지 나눗셈인지 가리는 것과 같은 문제다.

| 코드 | `<` 직전 토큰 | 판정 |
|---|---|---|
| `return (<div>` | `(` | JSX |
| `'k': <Comp />,` | `:` | JSX |
| `=> <b>x</b>` | `=>` | JSX |
| `if (a < b)` | 식별자 `a` | 비교 연산자 |
| `const x: Array<number>` | 식별자 `Array` | 제네릭 |

### JSX 안에서의 처리

| 구간 | 처리 |
|---|---|
| 여는 태그 안 속성값 `"…"` `'…'` | 문자열로 통과 |
| 속성값의 `{ … }` | JS 규칙으로 훑는다 (`x={ n /*c*/ }` → `x={ n }`) |
| 태그 사이 텍스트 | **원문 그대로.** 주석 판정을 하지 않는다 |
| 자식 자리의 `{ … }` | JS 규칙으로 훑는다 |
| `{/* … */}` | 통째로 삭제. `{ }` 만 남기면 지저분하다 |
| 중첩 태그 · `<br />` · 조각 `<>…</>` | 깊이를 세어 짝을 맞춘다 |

### 판별

2층 점수에서 JS 가 이긴 뒤, 아래 중 하나가 있으면 JSX 로 넘긴다.

`className=` · `return ( <` · `=> <태그` · `<>…</>` · `<대문자시작 />` 또는 `<대문자시작 속성=`

### 한계

제네릭 화살표 함수 `const f = <T,>(x: T) => x` 는 `<` 가 식 자리에 있어 JSX 로 잡힌다.

`.tsx` 에서만 쓰는 드문 문법이라 그대로 둔다.

## 10. 대응하지 않는 것

- **Java 유니코드 이스케이프** — 소스의 `\u002F\u002F` 는 렉싱 전에 `//` 로 치환되어 줄 주석이 된다 (JLS 3.3).
  대응하면 스캐너 앞에 치환 단계가 하나 더 붙는다. 실무 코드에 나오지 않는다고 보고 넘긴다
- **힌트 위치 검증** — `SELECT` 절 바로 뒤가 아닌 자리의 `/*+ … */` 도 보존한다
- **SQL*Plus `REM` · `REMARK` 줄** — SQL*Plus 명령이지 SQL 주석이 아니라 SQL 규칙은 안 지운다
- **MySQL 백슬래시가 꺼진 모드**(`NO_BACKSLASH_ESCAPES`) — MySQL 규칙은 기본 모드대로 `\'` 를 이스케이프로 본다
- **셸 `"$(…"…"…)"`** — 큰따옴표 안 명령 치환 속 따옴표는 따라가지 않는다. git 테스트 1,303개에서 문제가 된 파일은 없었다
- **셸 산술식 `$(( a << b ))`** — `<<` 뒤가 영문자면 heredoc 으로 본다. 그러면 그 뒤를 남기는 쪽으로 틀려서 내용은 안 깨진다
- **YAML 여러 줄 따옴표 스칼라** — `"…` 가 다음 줄로 넘어가는 경우는 문자열 보호가 줄 경계를 넘지 않는다
- **배치 `cmd & rem …`** — 줄 맨 앞이 아닌 `REM` 은 안 지운다
- **판별이 짧은 파일에 약하다** — `@hostname` 한 줄짜리 배치, 주석 + 명령 한 줄짜리 셸은 판별이 흔들린다. 목록에서 직접 고른다

## 12. MySQL · MariaDB

**문서** — 2절 표의 MySQL·MariaDB 행.

- `--` 는 뒤가 공백·제어문자·끝일 때만 주석이다. `SELECT 5--1` 은 5-(-1) 이라 남긴다
- **실측** 2026-09-26 — Dolibarr 의 `-------------` 구분선은 규칙대로면 마지막 `--` 만 주석이라,
  돌릴 때마다 두 글자씩 줄어 멱등이 깨졌다. 그래서 **줄 머리의 `--`**, **공백 뒤 대시 세 개 이상**은 뒤와 상관없이 주석으로 본다.
  `5--1` 같은 식 중간 두 개짜리는 그대로다
- 문자열은 `\'` 백슬래시와 `''` 겹치기 둘 다 이스케이프다. Oracle 규칙으로 돌리면 `'it\'s -- x'` 뒤를 주석으로 보고 코드를 지운다
- `#{id}` `#id#` 는 마이바티스·iBATIS 인자라 주석으로 안 본다. 매퍼 XML 안 SQL 은 계속 Oracle 규칙을 쓴다 — `#` 을 주석으로 보면 `#{}` 가 사라진다
- 판별 — SQL 이 이긴 뒤 백틱 식별자·`/*!`·`ENGINE=`·`AUTO_INCREMENT`·`ON DUPLICATE KEY`·줄머리 `#`·`UNSIGNED`·`TINYINT` 류·`DEFAULT CHARSET`·`LOCK TABLES` 중 하나가 있으면 MySQL.
  `/*!` 뒤 다섯·여섯 자리 버전 번호는 1층 판별이다 — 덤프가 문자열 안 JSON 때문에 JS 로 오판되던 것

## 18. 주석을 지우지 않은 줄은 건드리지 않는다

**실측** 2026-09-26 — 화면 옵션(끝 공백 정리·빈 줄 합치기)이 주석 없는 줄에도 걸려서, `.properties` 38개의 `Input ` 같은 끝 공백 값이 바뀌고

- 끝 공백 정리는 **주석을 지운 줄**에만 한다
- 빈 줄 합치기는 **지운 주석 줄이 끼어 있던 빈 줄 묶음**에만 한다
- 줄 주석을 지울 때 `\r` 은 남긴다. CRLF 파일의 줄 끝이 섞이지 않는다
