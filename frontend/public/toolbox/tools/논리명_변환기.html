1. 공통표준단어

3번 컬럼 목록의 물리명을 논리명으로 바꿀 때 쓰는 단어 사전.
매칭은 물리명을 _ 로 쪼갠 토큰 단위로 한다.
ITEM,상품 · ID,아이디 ← 영문약어,한글단어 2열짜리 CSV. 단어 조각이 한 줄씩
컬럼 물리명 ITEM_ID
① _ 기준으로 쪼갠다 └ ITEM+ID
② 단어를 매칭시킨다 └ ITEM→상품 · ID→아이디
└ 상품아이디 = 논리명
파일 받는 곳 — 공공데이터포털, 로그인 불필요
검색어 공공데이터 공통표준단어 또는 아래 주소
https://www.data.go.kr/data/15156439/fileData.do←행정안전부_공공데이터 공통표준단어_YYYYMMDD.csv
⬇ 파일을 여기로 끌어다 놓아도 된다
파일을 넣으면 자동 반영된다. 열 선택을 고쳤으면 3번의 [변환 실행] 을 다시 누른다.

2. 기관표준단어 (선택)

3번 컬럼 목록의 컬럼명·테이블명을 논리명(한글)으로 바꿀 때 쓰는, 기관이 자체 정의한 사전. 단어 조각과 통짜를 한 파일에 섞어 넣는다.
· 단어 조각 (STAT → 통계) — 물리명을 _ 로 쪼갠 토큰 조회에 참여한다. 조회 순서는 아래 «토큰 조회 우선순위»가 정한다.
· 통짜 (TB_CUST_MST → 고객마스터) — 컬럼명·테이블명 전체와 글자까지 같으면 쪼개지 않고 그 값이 바로 채택된다. 대소문자만 무관.
통짜로 적은 값은 다른 매칭 결과보다 앞서므로 강제 지정이 된다 — 조립 결과가 어색한 컬럼(SVC_TY_CD → 봉사TY코드)을 서비스유형코드 로 못박는 식.
아래 «토큰 조회 우선순위» 는 같은 약어를 기관표준단어와 공통표준단어가 다르게 정의했을 때 어느 쪽 뜻을 쓸지 고른다.
겹치는 약어가 없으면 어느 쪽으로 두든 결과가 같다.
5번 «미등록 약어 랭킹» 에 직접 친 한글은 어느 쪽으로 두든 두 파일보다 앞선다. 공통표준단어 CSV 는 여기 말고 1번에 넣는다.
⬇ 파일을 여기로 끌어다 놓아도 된다

3. 컬럼 목록 (컬럼 1건 = 1행)

변환 대상. 논리명으로 바꿀 컬럼과 테이블을 여기서 받는다. 컬럼 1건 = 1행 이라 테이블명이 여러 줄에 걸쳐 반복된다.
필요한 열은 스키마 · 테이블명 · 컬럼명 셋. 테이블 목록은 테이블명을 중복 제거해 만드니 따로 넣지 않는다.
7번 FK 관계 추론까지 할 거면 PK 여부 · 컬럼순서 · 데이터타입 · 길이 를 같이 넣는다. 논리명 변환에는 안 쓰는 열이다.
넣는 것은 아래 링크의 조회쿼리 결과, 또는 회사 테이블정의서·컬럼정의서. 자세한 형식은 0번 입력 형식 안내 참고.
★ 산출물 SQL → 03 컬럼 정의서 의 쿼리로 뽑는다. PK정보(Y/N)·데이터타입·길이가 다 들어 있어 논리명·FK 추론 양쪽에 그대로 쓴다.
⬇ 파일을 여기로 끌어다 놓아도 된다
↓ 7번 FK 관계 추론용 — 논리명 변환에는 안 쓴다
파란 라벨 3개는 (없음) 이어도 동작한다. FK 추론 정확도만 떨어진다

4. 변환 결과

논리명은 여기서 고치지 않는다. 표준단어로 조립된 결과다.
바꾸려면 5번 랭킹에 약어별 한글을 넣거나, 2번 기관표준단어에 물리명을 통째로 등록한다. 그래야 다음 변환에도 남는다.

5. 미등록 약어 랭킹 — 빈도순

한글을 입력하면 즉시 재변환한다. 입력값은 이 브라우저에 저장되어 다음에 열어도 남는다.
한 번 넣은 약어는 매칭에 성공해 미매칭이 아니게 되므로 출현 0 으로 목록에 남는다.
«파일 정의와 충돌» 열은 그 약어를 공통표준단어·기관표준단어도 정의해 놓은 경우에만 채워진다. 가림 = 파일 뜻 대신 내 입력이 나간다, 밀림 = 내 입력이 안 쓰인다.
브라우저에 남은 옛 입력이 새로 넣은 파일을 덮는 일을 여기서 잡는다.
[랭킹 CSV 저장] 은 영문약어,한글입력 순서로 나온다 — 2번 기관표준단어에 그대로 넣거나 기존 정의서 뒤에 붙여도 된다.

6. 출력

스키마명 항상 포함 (OWNER.TABLE)
생성물은 텍스트다. 운영 DB 실행은 별도 승인 사항.
컬럼명만 모드 — 테이블명 열이 (없음).
컬럼 코멘트는 테이블명이 필요해(방언 무관) DDL 생성을 막았다. 매칭결과 CSV는 저장된다.
← 용어사전=테이블+컬럼 distinct(구분열) · 단어사전=3소스 통합(공통Y+기관+랭킹)

7. FK 관계 추론 — erwin 관계선용

물리 FK 가 없어도 컬럼명 규칙으로 부모–자식을 추론해 ALTER TABLE … FOREIGN KEY 문을 만든다. erwin 이 스크립트를 읽으면서 관계선을 자동으로 그린다.
생성물은 erwin 에 먹일 .sql 끝에만 붙인다 — 운영 DB 실행 금지. 기존 데이터가 무결성 위반으로 터진다.

왜 되는가

erwin 의 관계선은 모델 객체다. DB 에 FK 제약이 있든 없든 무관하다. 지금 관계선이 0인 이유는 erwin 의 한계가 아니라 먹인 스크립트에 FOREIGN KEY 문이 한 줄도 없어서다. RE(Reverse Engineer)는 스크립트에 적힌 것만 그린다.

적용 순서

항목내용
부모 PK 필수부모에 PK/UNIQUE 가 없으면 FOREIGN KEY 문이 바인딩되지 않아 관계선이 안 생긴다. 그래서 아래에서 모델전용 PK 문을 같이 생성한다.
PK 여부 열을 넣으면 이미 PK 가 있는 테이블은 자동으로 건너뛴다. 안 넣으면 전부 생성되므로 중복분을 손으로 지워야 한다 — 중복 PK 는 파싱 오류다
PK 아닌 컬럼 참조부모에 PK 가 있는데 추론된 부모키가 그 PK 가 아니면 PRIMARY KEY 를 또 못 만든다. 이때는 ADD CONSTRAINT UK_MDL_… UNIQUE 로 낸다. Oracle 문법상 유효하고, erwin 은 대체키(AK) 로 읽는다. erwin 이 관계선을 안 그리면 그 건은 부모를 바꾸거나 수기로 그린다
컬럼 마이그레이션관계가 생기면 부모 키가 자식으로 내려온다. 자식에 같은 이름 컬럼이 이미 있으면 그 컬럼이 FK 로 흡수된다 (컬럼이 새로 생기지 않음)
rolenameSPEC_CUS_ID → CUS(CUS_ID) 처럼 이름이 다르면 erwin 이 rolename 으로 처리한다. 정상 동작이고 관계선도 그려진다
타입 불일치자식 컬럼 타입이 부모와 다르면 erwin 이 부모 타입으로 덮어쓸 수 있다. 그래서 기본값이 «타입 불일치 제외» 다
관계 표기전부 Non-Identifying(점선) 으로 나온다. 실제 FK 5건과 시각적으로 구분돼 오히려 낫다
FK 안 뱉게모델에 관계선만 두고 DDL 에는 FK 를 안 넣으려면 Forward Engineer → Schema Generation 에서 Referential Integrity 체크 해제. 제출물이 PNG 면 신경 안 써도 된다
