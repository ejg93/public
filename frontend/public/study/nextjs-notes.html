파일 지도 — Spring 자리에 무엇이 오나

Next 프로젝트를 처음 열었을 때 어느 파일이 Spring의 무엇 자리인지부터 잡는다. 대응이 안 맞는 것 두 개가 특히 헷갈린다.

포트폴리오 프로젝트의 실물이다. 전부 rewrites 뿐이다.

// next.config.js
async rewrites() {
  return [
    { source: '/toolbox',        destination: '/toolbox/toolbox.html' },
    { source: '/tools/:path*',   destination: '/toolbox/tools/:path*' },
  ]
}

들어온 URL을 실제 파일 경로로 바꿔치기한다. 아파치 rewrite 규칙과 같은 일이고, 여기에 { source: '/api/:path*', destination: 'http://백엔드:8080/:path*' } 를 넣으면 그것이 「백엔드 연결」이다.

기억할 것 하나 — Globals.uploadPath 같은 런타임 값은 .env 로 간다. next.config 는 환경값 파일이 아니다.

세 축

축 1 — 렌더링 시점

최초 HTML을 언제 만드는가. 골라 적는 것이 아니라 코드를 보고 Next가 판정한다.

만드는 시점사용자마다 다르게예
SSG빌드 때 1번불가약관, 소개, 학습 노트
ISR빌드 + N초마다불가상품 목록
SSR요청마다가능장바구니, 마이페이지

고르는 게 아니라 판정된다

// 쿠키·헤더·searchParams 안 씀 → SSG
export default async function Page() {
  return <div>이용약관…</div>
}

// cookies() 를 씀 → SSR 로 자동 강등
export default async function Page() {
  const jar = await cookies()
  return <div>{jar.get("name")}님</div>
}

누구 쿠키인지 빌드 때는 알 수 없으니 미리 만들 방법이 없다. cookies() headers() cache:"no-store" 가 그 스위치다.

CSR은 이 표에 없다. 서버가 빈 <div id="root"> 만 주고 브라우저가 전부 그리는 방식은 옛 React SPA(CRA·Vite)나 Pages Router 얘기다. App Router는 항상 내용이 채워진 HTML을 준다. 「4번째 선택지」로 외우면 계속 꼬인다.

SSG는 이미 만들어 본 적 있다

사내 시스템 화면을 브라우저로 한 번 열어 그 HTML을 통째로 저장해 둔 파일이 정확히 SSG 결과물이다. 한 번 렌더된 HTML을 파일로 떠 둔 것이라 DB 없이도 열린다. <c:if> 는 판정이 끝나 사라졌고 결과만 남았다.

한계까지 같다. 저장한 그 시점, 그 사용자로 굳어 있다. 권한 코드가 빈 값이면 <c:if> 로 감싼 영역이 통째로 비어 버리는데, 그것이 SSG의 제약 그 자체다.

축 2 — 코드가 브라우저로 가나

"use client" 는 「브라우저에도 보내라」는 표시다. 「브라우저에서만 돈다」가 아니다. 이 한 글자 차이가 제일 많이 꼬이는 지점이다.

판단 기준 — 질문 두 개

절을 다 읽기 전에 이것부터 잡아 두면 나머지가 전부 따라온다. 컴포넌트 하나를 앞에 두고 두 질문을 던진다.

하려는 일서버에서 미리 할 수 있나행동하는 순간 실행돼야 하나판정
목록 조회해서 표 그리기가능아니오서버
약관 본문 출력가능아니오서버
정렬 버튼 클릭불가예클라이언트
입력값 검증 표시불가예클라이언트
사이드바 접기불가예클라이언트
로그인한 사람 이름 찍기가능아니오서버
둘째 질문에 「예」인 조각만 라면으로 만든다. 화면 전체가 아니라 그 조각이다. 페이지 최상단에 "use client" 를 붙이면 아래 전부가 딸려 간다.

먼저 — 청크가 무엇인가

새로운 개념이 아니다. 번들러가 코드를 쪼개 만든 .js 파일 한 덩어리를 청크라고 부를 뿐이다.

왜 쪼개나 — 전부 한 파일이면 화면 하나 열 때 다른 화면 코드까지 전부 받아간다. 그래서 화면별로 가르고, 두 화면 이상이 쓰는 것은 공용으로 뽑는다.

여는 화면받아가는 청크
모든 화면framework-….js — React 본체
main-app-….js
app/layout-….js — 레이아웃에 클라이언트 컴포넌트가 있을 때만
/위 + app/page-….js
/youtube위 + app/youtube/page-….js (다른 화면 것은 안 받음)

JSP로 치면 이것과 목적이 같다.

<script src="/js/common.js"></script>   <!-- 전 화면 공통 -->
<script src="/js/report.js"></script>   <!-- 이 화면만 -->

차이는 파일을 손으로 나누느냐, 번들러가 import 그래프를 따라가 자동으로 나누느냐다.

로컬 PC에 저장되나 — 저장되긴 하지만 폴더에 .js 파일로 놓이는 것이 아니라 브라우저 HTTP 캐시로 들어간다. <script src="/js/common.js"> 를 받을 때와 완전히 같다. 청크라서 특별한 것이 아니다. 자세한 것은 번들과 캐시 절에 있다.

하이드레이션 — 마른 HTML에 동작을 붓는다

이름 그대로다. 건조식품에 물을 붓는 것(hydration). 모양만 있는 HTML에 JS를 부어 움직이게 만드는 단계다.

useState 가 이때 붙는 이유

서버는 false 로 한 번 계산하고 끝이다. 그 값을 기억하는 주체가 없다. 하이드레이션이 살아 있는 상태 칸을 메모리에 만들어야 setCollapsed(true) 가 의미를 가진다.

하이드레이션 전하이드레이션 후
collapsedHTML에 박제된 결과 (width:var(--sidebar-w))살아 있는 변수 · 바꿀 수 있음
onClick없음실제 DOM에 붙음
화면보인다보인다 (다시 안 그림)
하이드레이션 불일치 — 여기서 제일 많이 터진다. 서버가 그린 HTML과 브라우저가 다시 실행한 결과가 다르면 React가 경고를 뱉고 다시 그린다. 
"use client"
const [t] = useState(new Date().toLocaleTimeString())  // 서버 시각 ≠ 브라우저 시각
const w   = window.innerWidth                          // 서버엔 window 가 없다 → 터짐
"use client" 를 「브라우저 전용」으로 오해하면 정확히 이 버그를 만든다. 1단계가 서버에서 돈다는 것을 놓쳐서 생기는 일이다.

증거 — 실제 빌드 산출물

포트폴리오의 components/Sidebar.tsx 는 'use client' 가 붙어 있다. 그런데 빌드된 정적 HTML 파일 안에 마크업이 완성된 채로 들어 있다.

$ grep -o "STOCK SIM.\{0,60\}" .next/server/app/about.html

STOCK SIM</div></div></a></nav><div style="margin-top:auto">…
이 한 줄이 결론이다. 'use client' 컴포넌트가 SSG로 미리 렌더링되어 HTML 파일에 들어 있다. 축 1과 축 2가 서로 독립이라는 뜻이고, "use client" 가 CSR이 아니라는 뜻이다.

무엇이 되고 무엇이 안 되나

서버 컴포넌트 (기본)클라이언트 컴포넌트
코드가 브라우저로안 감감 (.js 청크)
서버에서 HTML 생성함함
브라우저에서 다시 실행안 함함
await db.query()가능불가
useState onClick불가가능
window document불가가능하나 첫 렌더 때는 없음
비밀값 두기안전노출

사내 시스템으로 옮기면 서버 컴포넌트 = JSP 본문, 클라이언트 컴포넌트 = common.js 다. JSP는 언어가 달라 저절로 갈렸고, React는 같은 언어라 사람이 선을 긋는다.

왜 서버 컴포넌트는 onClick·useState 를 못 쓰나

db.query() 가 브라우저에서 안 되는 이유는 쉽다 — 소켓도 접속정보도 없다. 반대 방향은 덜 뚜렷한데, 뿌리는 같다.

onClick — 함수는 HTML로 적을 수 없다

// 서버 컴포넌트라고 치자
export default function Page() {
  return <button onClick={() => alert("hi")}>클릭</button>
}

서버가 보낼 수 있는 것은 HTML 문자열뿐이다. 그러면 무엇을 보내나.

<button>클릭</button>

() => alert("hi") 는 서버 메모리에 있는 함수 객체다. 문자열로 적어 보낼 방법이 없다. 보내려면 코드를 보내야 하는데, 코드를 보내는 것이 곧 "use client" 다. 순환이라 정의상 불가능하다.

JSP는 어떻게 했나 
<input type="button" onclick="fn_orderExcel('9');" />
이것은 문자열 속성이지 함수가 아니다. 작동한 이유는 fn_orderExcel 이 같이 내려간 <script> 안에 전역 함수로 있었기 때문이다. JSP도 결국 JS를 브라우저로 보냈기 때문에 onclick이 먹은 것이고, 원리가 같다.

대신 문자열이라 렌더 시점의 값을 붙잡지 못한다. 그래서 전역 변수로 빼거나 id 로 다시 찾아야 했다. React의 onClick 은 진짜 함수 참조라 그 자리의 값을 그대로 쥔다 — 그 대가가 코드 배송이다.

useState — 서버엔 값을 담아둘 곳이 없다

useState 가 요구하는 것은 둘이다.

  1. 값을 담아둘 살아 있는 메모리
  2. 값이 바뀌면 다시 그릴 주체

서버 컴포넌트는 한 번 돌고 응답을 보내면 끝이다. 함수도 변수도 사라진다. 그리고 HTTP는 응답을 보낸 뒤에 서버가 그 화면을 고칠 방법이 없다.

<% int count = 0; %>   <%-- 버튼 누를 때마다 올라가는 카운터가 되나 --%>

안 된다. 응답이 끝나면 없어진다. 상태가 아니라 렌더 중 임시값이다. 그래서 JSP 화면의 상태는 전부 JS 쪽에 있었다.

var gradeCd = "";   // ← 브라우저 메모리. 탭이 열려 있는 동안 살아 있다

제약 셋이 같은 뿌리에서 나온다

하려는 것필요한 것서버에 있나브라우저에 있나
db.query()DB 소켓 · 접속정보있음없음
onClick브라우저 안의 함수 실체코드가 안 감감
useState살아 있는 메모리 · 다시 그릴 주체응답 끝나면 소멸탭 열린 동안 유지
한 문장으로 — 코드가 서버에만 있으면 DB는 되고 이벤트·상태는 안 된다. 코드가 브라우저에도 가면 이벤트·상태는 되고 DB는 안 된다. 하이드레이션은 그 결과지 원인이 아니다.

그래서 실무에서는 섞는다

서버 컴포넌트에 <button> 을 넣을 수는 있다. 핸들러만 못 붙인다. 그래서 그 조각만 떼어 낸다.

// page.tsx — 서버 컴포넌트
export default async function Page() {
  const rows = await db.query("SELECT …")     // ← 서버만 가능

  return (
    <div>
      <table>{rows.map(r => <tr key={r.id}>{r.nm}</tr>)}</table>
      <RefreshButton />            {/* ← "use client". 이 조각만 라면 */}
    </div>
  )
}

표는 밥, 버튼만 라면이다. 둘 다 필요한 화면이라고 전체를 라면으로 만들 이유가 없다.

예외 하나 — <form action={서버함수}> 는 서버 컴포넌트에서도 동작한다. 폼 제출이 브라우저 기본 동작이라 JS 없이도 되고, 함수를 보낼 필요가 없기 때문이다.

축 3 — 이동할 때 문서를 갈아엎나

Next는 URL이 바뀐다. 안 바뀌는 것은 URL이 아니라 문서 전체 리로드다.

URL전체 리로드뒤로가기·북마크
JSP <a href>바뀜함됨
JSP + AJAX안 바뀜안 함깨짐
Next <Link>바뀜안 함됨

사내 시스템에 가운데 방식이 그대로 있다

postData["searchDate"] = $("#searchDate").val().replace(/-/gi, '');
fnAjaxCall("/biz/orderEventSelectList.do", postData, renderEventList);

날짜를 바꿔 조회하면 표만 갈리고 URL은 그대로다. 그래서 조회 결과를 링크로 못 보내고, 뒤로가기를 누르면 조회 이전이 아니라 이전 화면으로 튀고, 새로고침하면 결과가 날아간다.

반면 orderList.do?tab=T02 는 URL에 상태가 있어 전부 된다. 한 시스템 안에 두 방식이 섞여 있는 것이고, Next는 이 구분 자체가 없다.

덤 — 이동할 때 받는 것은 HTML 전체가 아니라 바뀐 부분의 데이터뿐이다. 레이아웃은 안 건드리니 머리·꼬리 몫은 아예 안 받는다. 화면에 보이는 <Link> 는 미리 당겨 두므로 클릭 시점엔 이미 손에 있다.

구조

클라이언트 컴포넌트가 데이터를 얻는 길

"use client" 붙은 파일은 SELECT를 직접 못 한다. jQuery가 SELECT를 못 하는 것과 같은 얘기이고, 해법도 같다.

왜 직접 못 하나

  • 브라우저에 DB 드라이버가 없다 — 소켓을 못 연다
  • DB 포트는 WAS에만 열려 있지 브라우저에 안 열려 있다
  • 열려 있다 쳐도 접속정보가 크롬에서 그대로 읽힌다

① props — 부모 서버 컴포넌트가 조회해 넘김

// page.tsx — 서버
export default async function Page() {
  const rows = await db.query("SELECT OCCUR_DT, TYPE_NM FROM ORDER_EVENT WHERE …")
  return <EventTable rows={rows} />
}

// EventTable.tsx
"use client"
export default function EventTable({ rows }) {
  const [sort, setSort] = useState("asc")
  return <table>{rows.map(…)}</table>
}
개인정보 SR과 직결되는 함정. props로 넘긴 것은 화면에 안 그려도 브라우저에 전부 간다. row를 통째로 넘기고 이름만 찍으면 주민번호·연락처가 HTML 안에 실려 크롬 소스보기로 읽힌다. 서버에서 필요한 컬럼만 골라 넘겨야 한다.

② route.ts + fetch — 기존 AJAX 방식 그대로

// app/api/act-app/route.ts  ← 서버에서만 돎
export async function GET(req) {
  const date = req.nextUrl.searchParams.get("date")
  const rows = await db.query("SELECT … WHERE EVENT_DT = ?", [date])
  return Response.json(rows)
}

③ Server Action — 배선을 프레임워크가 깔아줌

// actions.ts
"use server"
export async function getOrderEvent(date: string) {
  const session = await auth()                    // ← 이 줄이 없으면
  if (!session) throw new Error("unauthorized")   //   남의 데이터가 그대로 나간다
  return db.query("SELECT … WHERE EVENT_DT = ?", [date])
}

// 클라이언트
const rows = await getOrderEvent(date)   // 함수 호출처럼 생겼지만 실제론 HTTP POST

브라우저에 가는 것은 함수 본문이 아니라 그 함수를 가리키는 id 문자열뿐이다.

제일 위험한 지점. 함수처럼 생겼다고 안전한 게 아니라 URL 없는 공개 엔드포인트다. AuthInterceptor 가 preHandle 에서 일괄로 걸러 주던 것이 자동으로는 없다. Server Action 하나하나에서 직접 확인해야 한다.

판단 기준 한 줄

「이 값이 크롬 개발자도구에 노출돼도 되나」 — 안 되면 서버에 남기고 화면에 필요한 것만 골라 내려보낸다. 클라이언트 컴포넌트는 받은 것을 그리고 이벤트를 처리하는 자리지 데이터를 캐 오는 자리가 아니다.

클라이언트 쪽은 폴더가 아니다

사용자 PC의 어떤 프로젝트 폴더에 저장되지 않는다. 그냥 일반 정적 리소스라 브라우저 HTTP 캐시로 들어간다. 크롬·윈도우 기준 물리 위치는 대략 이렇다.

%LOCALAPPDATA%\Google\Chrome\User Data\Default\Cache\Cache_Data\

열어 봐도 layout-xxx.js 같은 파일은 없다. 여러 응답이 뭉쳐진 불투명 바이너리이고 Ctrl+Shift+Del 로 날아간다. 개발자가 관리하는 대상이 아니고, 볼 때는 개발자도구 Network·Sources 탭에서 본다.

확인하는 법 — 크롤러로 사이트를 긁어 보면 브라우저가 실제로 받아간 JS·CSS가 그대로 파일로 떨어진다. Next 사이트를 긁으면 저 청크들이 쌓인다.

파일명 해시가 하는 일

코드를 한 글자 고치면 해시가 바뀌고 → URL이 바뀌고 → 브라우저가 캐시를 못 쓰고 → 새로 받는다. 그래서 이 파일들은 1년짜리 immutable 로 내려도 안전하다.

JSP 프로젝트는 이것을 손으로 한다. ver 을 안 올리면 사용자가 옛 JS를 계속 쓴다. 배포하고 「왜 안 바뀌죠」가 나오는 원인이 보통 이것이다.

ProjectShop은 정적 라우트가 둘뿐이다. 이유는 layout.tsx 에 있다.

layout.tsx → <SiteHeader/> → apiSessionOptional() → cookies() 읽음

src/lib/api-session.ts 가 next/headers 의 cookies() 를 쓰고 cache: "no-store" 도 쓴다. 쿠키를 읽는 순간 빌드 때 못 만든다. 레이아웃에 들어갔으니 약관 페이지처럼 로그인과 무관한 화면까지 전부 SSR이 됐다.

지금 규모에서는 문제가 아니다. 고치려면 머리의 로그인 표시 부분만 떼어 따로 처리하는 식이 된다. 알고만 있으면 되는 항목이다.

     <Link> 쓰면 끝

한 장 요약

축질문값정하는 법
1HTML을 언제 만드나SSG · ISR · SSR자동 판정 (cookies() 쓰면 SSR)
2코드가 브라우저로 가나서버 · 클라이언트 컴포넌트"use client"
3이동할 때 갈아엎나리로드 · 클라 네비<Link> 쓰면 끝
  • CSR — 옛 React SPA 방식. App Router에는 없다
  • "use client" — CSR이 아니다. 서버 렌더링은 그대로 일어난다
  • layout.tsx — 축이 아니다. 전 화면에 붙는 파일이고 축 1·2를 전파시킨다
제일 많이 걸리는 함정 하나만 다시 — "use client" 를 붙여도 서버 렌더링은 그대로 일어난다. 이것만 잡히면 나머지는 안 꼬인다.
