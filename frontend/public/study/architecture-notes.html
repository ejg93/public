1. Tier vs Layer

개발자 필독 | 티어와 레이어 구분 #개발자개념장착 (5분 32초)

구분 Tier Layer
원래 뜻 층, 단계 층, 겹
관점 물리적 분리 논리적 분리
위치 다른 서버 / 프로세스 같은 소프트웨어 구성 내
통신 네트워크 호출 함수 호출
예시 Client ↔ Server ↔ DB Controller → Service → Repository

Tier : SW System을 구성하는 물리적으로 분리된 실행 계층

  • 네트워크로 연결 → 요청/응답이 양방향으로 오감
[Client] ↔ [Server] ↔ [DB]

Layer : SW 구성을 역할과 책임에 따라 논리적으로 나눈 구조

  • 함수 호출로 연결 → 의존 방향이 단방향 (상위 → 하위만 호출, 역방향 금지)
Presentation (Controller)
      ↓ 함수 호출
  Business (Service)
      ↓ 함수 호출
 Data Access (Repository)

핵심 차이: Tier는 ↔ (네트워크 왕복), Layer는 → (의존 단방향)
Repository가 Service를 직접 호출하면 Layer 위반 — 의존성 역전이 필요한 경우 DIP 패턴 사용

둘은 독립적 — 1-Tier 안에 3-Layer 가능, 3-Tier 각각이 또 내부 Layer 가질 수 있음

Tier 역사: 2-Tier (Fat Client 시대, 1990년대 ~ 2000년대 초)

[클라이언트 (Fat Client)]   ← 1st Tier
  설치형 데스크톱 .exe
  화면 + 업무로직 + SQL 전부 클라이언트에 존재
       ↕ 직접 연결
      [DB 서버]             ← 2nd Tier
  • 대표 기술: Visual Basic, Delphi, PowerBuilder, C++ Builder
  • 클라이언트가 DB에 직접 접속 권한을 가짐

2-Tier의 문제점 — 공통 원인: "업무 로직이 클라이언트에 있었기 때문"

문제 내용
보안 클라이언트가 DB 직접 접속 권한 보유 → DB 접속 정보 유출 시 직접 접근 가능
유지보수 업무 로직이 여러 클라이언트에 분산 → 정책 변경 시 모든 클라이언트 수정·재배포 필요
확장성 커넥션 풀이 클라이언트 PC마다 분산 → DB가 감당할 커넥션 수를 중앙에서 통제 불가

이 문제들이 3-Tier (Server 계층 추가) 탄생의 이유

핵심: "통제"는 중간 계층이 있어야 가능. DB는 데이터 저장이 목적이지 트래픽 관리가 목적이 아님.
2-Tier = DB가 최전선. 커넥션 한계 초과 시 그냥 거부, 대기열/안내 없음.
3-Tier = App Server가 트래픽 통제 → DB엔 정해진 수만 연결 (커넥션 풀)

Tier 역사: 3-Tier (App Server 등장, 1990년대 후반 ~ 2000년대)

[클라이언트 (화면만)]   ← 1st Tier
       ↕ 네트워크
  [Application Server] ← 2nd Tier  ← 업무 로직 여기로 이동
       ↕ 네트워크
      [DB 서버]         ← 3rd Tier

App Server의 역할 (2-Tier 문제 전부 해결):

  • 업무 로직을 서버로 이동 → 클라이언트 재배포 불필요
  • DB 커넥션 풀 중앙 관리 → 확장성 확보
  • 트랜잭션 관리
  • 클라이언트와 DB 사이의 보안 경계 역할

C/S 기반: Tuxedo, CORBA, COM+, 초기 EJB
Web 기반: WebLogic, WebSphere (WAS) — 웹 시대로 넘어가며 주류

웹/모바일 시대 — 구조 변화 흐름

시기 변화
2000년대 초 브라우저가 클라이언트가 됨 → Fat Client 사라지기 시작
RIA 시대 ActiveX, Flash, Applet으로 브라우저가 다시 무거워짐 → 사실상 Fat Client 재현
핵심 변화 브라우저는 일반적으로 DB에 직접 연결하지 않는다 (DB 드라이버 부재, 보안 정책, 계정 노출 위험)
2010년대 HTML5 표준화 · ActiveX 퇴출 → 브라우저가 진정한 Thin Client로 / 스마트폰 앱 등장
현재 REST API / GraphQL이 프론트-백 경계의 표준

3-Tier 원칙은 그대로 — 클라이언트 / API 서버 / DB로 이름만 바뀐 것

현대 Architecture — N-Tier

[앱 / 브라우저 클라이언트]
       ↕ HTTPS / REST / GraphQL
      [API 서버]
           ↕
    [캐시 / 메시지큐]
           ↕
      [DB / 저장소]
  • N-Tier = 3-Tier 이상으로 계층이 늘어난 구조
  • 캐시, 메시지큐, 인증 서버 등이 별도 Tier로 분리
  • MSA에서는 여러 개의 3-Tier 서비스가 공존

Tier가 늘수록 유연성↑ 복잡성↑ — 적절한 수준이 중요

Tier "물리적 분리"의 현대적 해석

  • 고전: 기계(서버)가 물리적으로 다름
  • 현대 기준: 네트워크 없이는 통신 불가능한 경계가 존재하면 Tier로 취급
  • Docker 컨테이너도 Tier — 같은 기기여도 HTTP/TCP 쳐야 통신 가능
  • 판단 기준: 네트워크 호출 필요? → YES = Tier, 함수 호출로 끝? → YES = Layer
실제 사례 (Spring + MyBatis 환경):
[브라우저] ↔ [Spring 서버] ↔ [MySQL]   ← Tier (네트워크 경계)
              ↑ 서버 내부
         Controller (@Controller)
              ↓
          Service (@Service / ServiceImpl)
              ↓
         Repository (@Mapper / MyBatis)    ← Layer (함수 호출)

Layer 단방향이어야 하는 이유

  • 역방향 호출 시 순환 의존 발생 → 수정 한 곳이 전체에 영향
  • 계층 간 책임 경계 붕괴 → 어디서 뭘 해야 하는지 모호
  • 테스트 불가 → Repository 단위 테스트하려면 Service, Controller까지 올려야 함
  • Service 인터페이스 + ServiceImpl 구현체 분리 = 상위 계층이 구현체가 아닌 추상에만 의존하도록 강제 (각 계층은 자기 바로 아래 인터페이스만 알면 됨)

[심화] 웹 vs 게임 통신 방식 비교

웹 실시간 게임
연결 요청마다 새로 (HTTP) 상시 유지 (TCP Socket / WebSocket)
상태 유지 세션ID 쿠키 연결 자체가 상태
프로토콜 TCP 위치/이펙트 → UDP, 결제/채팅 → TCP

HTTP는 Stateless — 요청/응답 후 연결 끊김. 로그인 유지는 세션ID 쿠키로 흉내냄.

게임 데이터 분리:

서버 보유 (검증 필요): 위치, 체력, 골드, 스킬 판정
클라 보유 (렌더링용): 스킨, 모델, 이펙트, 미니맵
→ 커스텀 스킨이 본인 화면에만 적용되는 이유

UDP 쓰는 이유 — 위치 패킷 하나 손실돼도 다음 프레임에 새 위치 옴. 재전송 기다리는 딜레이가 더 치명적.
보간(interpolation) 으로 손실된 위치 추정. 스킬 적중 판정은 서버가 최종 결정.
→ "분명히 피했는데 맞음" = 핑 차이 + UDP 손실 + 서버 판정 타이밍 차이

[심화] 브라우저 제약

브라우저 = 샌드박스. TCP/UDP 직접 못 씀. 실시간 연결 우회책만 허용:

  • WebSocket — HTTP 업그레이드 후 양방향 유지 (채팅, 주식차트)
  • SSE — 서버→클라 단방향
  • WebRTC — 브라우저끼리 P2P (화상통화)

게임 클라이언트(.exe) = OS 위 직접 실행 → TCP/UDP 자유, 제약 없음.
브라우저 게임 성능 한계 / 플래시 망한 이유 = 이 샌드박스 제약 때문.

2. 모놀리식이 먼저입니다

모놀리식이 먼저 입니다. 😊 (4분 3초)

Why MSA?

MSA는 모놀리식 아키텍처의 한계에서 출발한 해결책.
그 한계를 모르면 MSA도 이해할 수 없음.

"모놀리식을 제대로 해본 사람이 MSA를 제대로 씁니다"

모놀리식이 커지면 나타나는 대표적인 한계
(Martin Fowler & James Lewis, 2014 / Conway's Law 기반)

한계 문제 MSA 해결책
배포 버튼 하나 바꿔도 전체 애플리케이션 재배포. 배포 범위·위험도 증가 서비스 단위 독립 배포
확장 특정 기능만 과부하여도 전체 애플리케이션을 함께 확장 서비스 단위 독립 스케일
협업 팀이 커질수록 변경 하나가 다른 팀 작업을 망침. 독립 개발 어려움 팀 단위 독립 개발 지원

이 한계를 직접 경험해봐야 MSA의 설계 결정들이 납득됨

[추가] 모놀리식 한계 보완

한계 문제 MSA 해결책
장애 격리 (SPOF) 결제 모듈 하나 죽으면 전체 서비스 다운 서비스별 독립 장애 격리
스케일링 비효율 트래픽 몰리는 기능만 키우고 싶어도 전체 애플리케이션을 스케일업해야 함 트래픽 몰리는 서비스만 스케일아웃 (주문 서비스만 10개 띄우기)
기술 스택 고착 전체가 한 언어/프레임워크에 묶임 서비스별 최적 스택 선택 가능 (추천 → Python, 결제 → Java)

[추가] MSA 단점 상세

영상에서 "관리 복잡성" 으로 묶인 것의 실체:

단점 내용
분산 트랜잭션 주문 + 결제 + 재고 동시 성공해야 하는데 중간 하나 실패 시 롤백 처리 매우 복잡
네트워크 레이턴시 함수 호출이 네트워크 호출로 바뀜 → 느려짐, 실패 가능성 추가
데이터 일관성 서비스마다 DB 분리 → 정합성 맞추기 어려움
배포 파이프라인 서비스 수만큼 CI/CD 파이프라인 관리
로컬 개발 서비스 여러 개 동시 기동해야 개발 가능

결론: 모놀리식 문제 = 결합도, MSA 문제 = 분산 복잡성. 트레이드오프.
시스템이 충분히 크지 않으면 MSA가 오히려 일을 늘림.

STEP 2 — 개념은 미리 알아둬도 좋습니다

채용공고에서 MSA 환경은 매우 흔해짐. 구현보다 먼저 개념은 알아두는 것이 좋음.

이 정도는 미리 — 개념 수준으로

  • MSA가 왜 등장했는가
  • 서비스 분리의 기준
  • API Gateway의 역할
  • 서비스 간 통신 방식 (동기 / 비동기)
  • 분산 트랜잭션 문제

아직은 괜찮음 — 구현은 나중에

  • Kafka 직접 구축
  • Kubernetes 운영
  • Service Mesh 설정
  • 분산 추적 (Jaeger 등)

기본기 없이 배우면 기술 스택 암기에 그침

STEP 3 — 기본기가 되면 MSA가 납득됩니다

모놀리식의 고통을 직접 겪은 사람은 MSA의 복잡한 설계 결정들이 왜 그렇게 됐는지 자연스럽게 납득됨

이때 비로소 보이는 것

  • 트랜잭션 처리 → 분산 트랜잭션의 어려움
  • DB 설계 → 서비스별 DB 분리 이유
  • 캐싱 → 분산 캐시 전략
  • 인증 → API G/W 인증 위임 구조

이때 공부하면 효과적인 것

  • Kafka / RabbitMQ (MSA 외에도 널리 쓰임)
  • Kubernetes · Service Mesh
  • Service Mesh (Istio 등)
  • 분산 추적 · 모니터링

3. 모놀리스 vs MSA

스타트업 딜레마! 모놀리스냐 MSA냐? (7분 20초)

판정 질문 — 표를 읽기 전에 이것부터

개념 질문 예 →
모놀리스 전체를 한 번에 배포해도 팀끼리 안 부딪히나? 한 덩어리로 둔다
MSA 기능마다 배포 주기·확장량·장애 범위를 따로 가져가야 하나? 서비스로 자른다

둘 다 「아니오」거나 헷갈리면 모놀리스다.
MSA는 필요가 증명됐을 때 지불하는 운영 비용이지 기본값이 아니다.

구분 모놀리스 MSA
배포 단순 복잡
확장성 비효율적 효율적
장애 격리 취약 우수
기술 복잡도 낮음 (구조) 높음 (운영)

콘웨이의 법칙 (Conway's Law)

시스템의 구조는 그것을 만드는 조직의 커뮤니케이션 구조를 닮아간다는 법칙.

[3번 영상 복습 질문]

  1. 스타트업에서 모놀리스와 MSA 중 무엇을 선택해야 하는가?

    힌트 각도:

    • 사업 불확실성 — 초기에 규모를 알 수 있는가?
    • 트래픽 — 팀 크기보다 트래픽 폭발 가능성이 더 중요할 수도
    • 팀 구조 — Conway's Law: 조직이 분리 안 됐으면 MSA 해도 모놀리식처럼 됨

5. 트랜잭션 ACID

백엔드 개발자라면 반드시 알아야 하는, 트랜잭션 ACID (5분 54초)

판정 질문 — 이 연산 묶음을 트랜잭션으로 감쌀까

질문 예 →
중간까지만 반영된 상태가 DB에 남아도 되나? 감쌀 필요 없다
앞 연산이 성공하고 뒤가 실패했을 때, 앞 것도 없던 일이 되어야 하나? 트랜잭션으로 묶는다

트랜잭션이란?

여러 DB 연산을 하나의 논리적 작업 단위로 묶은 것. 전부 성공하거나 전부 없던 일이 되어야 함.

예: 계좌이체
1. A 계좌 -10,000원
2. B 계좌 +10,000원
→ 1만 성공하고 2가 실패하면? DB는 절대 그 상태로 남으면 안 됨

A — Atomicity (원자성)

트랜잭션 내 모든 연산은 전부 성공(COMMIT) 또는 전부 실패(ROLLBACK). 중간 상태 없음.

  • "All or Nothing"
  • 실패 시 DB는 트랜잭션 시작 전 상태로 되돌아감
  • 구현: UNDO 로그 (실패 시 이전 값으로 복구)

C — Consistency (일관성)

트랜잭션 전후로 DB의 무결성 제약 조건이 항상 유지되어야 함.

  • 잔액이 음수가 되면 안 된다는 규칙 → 트랜잭션 후에도 유지
  • NOT NULL, UNIQUE, FK 제약 등 모두 포함
  • 비즈니스 규칙을 DB가 보장
잔액 >= 0 제약이 있다면:
A 계좌 잔액 5,000원인데 10,000원 이체 시도 → 트랜잭션 거부

I — Isolation (격리성)

동시에 실행 중인 트랜잭션들은 서로의 중간 상태를 볼 수 없어야 함.

  • 트랜잭션 A가 진행 중일 때 트랜잭션 B는 A의 미완료 변경사항을 못 봄
  • 완벽한 격리 = 성능 저하 → 격리 수준(Isolation Level)으로 트레이드오프 조절
  • 다음 영상(6번)에서 격리 수준 4단계 상세 다룸
격리 낮음 ↔ 높음 문제 현상
격리 낮으면 Dirty Read, Non-Repeatable Read, Phantom Read 발생
격리 높으면 동시성 낮아짐, 성능 저하

D — Durability (지속성)

커밋된 트랜잭션의 결과는 장애가 발생해도 영구적으로 유지되어야 함.

  • DB 서버 다운, 정전 → 재시작 후에도 커밋된 데이터 보존
  • 구현: REDO 로그 (커밋 후 장애 시 로그로 복구)
  • COMMIT 응답을 받았다면 디스크에 쓰여진 것이 보장됨

ACID 한눈에

속성 핵심 한 줄 구현 수단
Atomicity 전부 or 없음 UNDO 로그, ROLLBACK
Consistency 제약 조건 항상 유지 DB 제약, 비즈니스 규칙
Isolation 중간 상태 안 보임 락, MVCC
Durability 커밋 = 영구 보존 REDO 로그, WAL

ACID는 DB가 "믿을 수 있는 저장소"임을 보장하는 4가지 약속.
이 중 하나라도 깨지면 데이터 정합성 보장 불가.

Spring에서 트랜잭션

@Transactional  // 이 어노테이션 하나가 ACID 전부 보장
public void transfer(Long fromId, Long toId, int amount) {
    accountRepository.decrease(fromId, amount);  // 실패하면
    accountRepository.increase(toId, amount);    // 전체 ROLLBACK
}

6. 트랜잭션 격리수준

트랜잭션 격리수준 4단계 완전 이해 (12분 19초)

판정 질문 — 위에서부터 「아니오」가 처음 나오는 줄이 필요한 수준이다

질문 아니오 → 최소
아직 커밋 안 된 남의 값을 읽어도 되나? READ COMMITTED
같은 행을 두 번 읽었을 때 값이 달라져도 되나? REPEATABLE READ
같은 조건으로 두 번 조회했을 때 행 수가 달라져도 되나? SERIALIZABLE

셋 다 「예」면 READ UNCOMMITTED로 충분하다.
아래 「현상 3가지」 표는 각 질문에 「예」로 답했을 때 실제로 무엇이 보이는지를 적은 것이다.

핵심 면접 질문

"왜 무조건 최고 수준(SERIALIZABLE)으로 설정하지 않나요?"
→ 격리 높을수록 락 범위 넓어짐 → 대기 트랜잭션 쌓임 → 처리량 저하. 신뢰성과 성능의 트레이드오프.

격리가 낮을 때 생기는 문제 현상 3가지

현상 설명 예시
Dirty Read 커밋 안 된 값 읽음 A가 롤백할 값을 B가 이미 읽어서 사용
Non-Repeatable Read 같은 쿼리 두 번 날렸는데 결과 다름 트랜잭션 중 다른 트랜잭션이 UPDATE·DELETE
Phantom Read 같은 조건 두 번 조회했는데 행 수 다름 트랜잭션 중 다른 트랜잭션이 INSERT 
Dirty Read:
  A: UPDATE money = 0           (미커밋)
  B: SELECT money → 0 읽음
  A: ROLLBACK → 다시 10000
  B는 존재한 적 없는 0을 읽은 것

Non-Repeatable Read:
  B: SELECT money → 10000
  A: UPDATE money = 5000; COMMIT
  B: SELECT money → 5000  ← 같은 트랜잭션인데 다른 결과

Phantom Read:
  B: SELECT COUNT(*) WHERE age > 20 → 5건
  A: INSERT 새 행 (age=25); COMMIT
  B: SELECT COUNT(*) WHERE age > 20 → 6건  ← 유령 행 등장

격리 수준 4단계 (낮음 → 높음)

단계 수준 Dirty Read Non-Repeatable Read Phantom Read 성능
1단계 READ UNCOMMITTED 발생 발생 발생 최고
2단계 READ COMMITTED 방지 발생 발생 높음
3단계 REPEATABLE READ 방지 방지 발생 중간
4단계 SERIALIZABLE 방지 방지 방지 최저

각 수준 설명

READ UNCOMMITTED — 커밋 안 된 것도 다 읽음. 실무 사용 거의 없음. Dirty Read 허용.

READ COMMITTED — 커밋된 것만 읽음. PostgreSQL·Oracle 기본값. 대부분 서비스에서 충분.

REPEATABLE READ — 트랜잭션 시작 시점 스냅샷 고정. 같은 SELECT 항상 같은 결과. MySQL InnoDB 기본값. MVCC로 구현.

SERIALIZABLE — 완전 직렬 실행. 모든 문제 방지. 락 경합 심해 처리량 급락. 금융 일부 배치 처리에서만 사용.

MVCC (Multi-Version Concurrency Control)

MySQL InnoDB가 REPEATABLE READ를 성능 저하 없이 구현하는 방법

락 없이 격리 구현:

  • 트랜잭션 시작 시점에 스냅샷 찍음 (Undo 로그에 이전 버전 보관)
  • 트랜잭션 안에서 SELECT는 스냅샷 기준으로 읽음
  • 남이 바꾼 건 스냅샷 기준으로 무시, 내가 직접 바꾼 건 즉시 반영
  • 읽기와 쓰기가 서로 블로킹 안 함
B 트랜잭션 시작 → 스냅샷: money=10000

A: UPDATE money=5000; COMMIT   ← DB 실제값 바뀜
B: SELECT money → 10000        ← 남이 바꾼 건 스냅샷 기준

B: UPDATE money=7000           ← 본인이 직접 바꿈
B: SELECT money → 7000         ← 본인 변경은 즉시 반영

B 트랜잭션 종료 후 새 조회 → 7000 (최신값)

실무 기본값

DB 기본 격리 수준
MySQL InnoDB REPEATABLE READ
PostgreSQL READ COMMITTED
Oracle READ COMMITTED
SQL Server READ COMMITTED

Spring @Transactional은 DB 기본값 따라감. 변경 필요 시 @Transactional(isolation = Isolation.SERIALIZABLE)

격리수준 적용 단위 — 테이블 아니고 트랜잭션(세션)

격리수준은 테이블·DB 전체에 고정되는 설정이 아님. 트랜잭션 단위로 그때그때 다르게 걸 수 있음.

@Transactional(isolation = Isolation.SERIALIZABLE)
public void monthEndInterestBatch() { ... }   // 이 트랜잭션만 SERIALIZABLE

@Transactional  // 기본값 (예: READ COMMITTED)
public void normalTransfer() { ... }          // 평소 이체는 기본 격리로 빠르게
  • 같은 테이블이라도 어떤 트랜잭션이 접근하냐에 따라 그 순간 격리수준이 다를 수 있음
  • 실무 패턴: 평상시 트래픽(이체·조회)은 기본 격리로 처리, 월말 이자 계산처럼 "계산 중 아무도 못 건드려야 하는" 배치 작업만 그 트랜잭션에 SERIALIZABLE 적용
  • 이런 배치는 보통 트래픽 적은 새벽 시간대에 짧게 실행 → 락 경합 비용 낮음
  • 세션 레벨(SET SESSION TRANSACTION ISOLATION LEVEL ...)로 커넥션 전체 기본값 바꾸는 것도 가능하지만, 실무에서는 필요한 트랜잭션에만 국소적으로 지정하는 게 일반적

SELECT ... FOR UPDATE (비관적 락)

스냅샷 무시하고 실제 최신값 읽으면서 동시에 락 걸기. "읽고 → 판단 → 쓰는" 패턴에서 사용.

SELECT * FROM item WHERE id = 1 FOR UPDATE;
-- 해당 행에 쓰기 락(exclusive lock)
-- 다른 트랜잭션의 UPDATE/DELETE → 대기
-- 다른 트랜잭션의 FOR UPDATE SELECT → 대기
-- 다른 트랜잭션의 일반 SELECT → 통과 (스냅샷 읽기라 락 안 봄)

스냅샷 읽기는 "남이 바꾼 거 안 보임" → 재고 10 읽고 차감했는데 실제론 이미 0이면 문제.
FOR UPDATE는 최신값 읽고 수정만 막음 (일반 읽기는 허용). 내 트랜잭션 끝날 때까지 다른 트랜잭션 수정 대기.

// Spring Data JPA
@Lock(LockModeType.PESSIMISTIC_WRITE)  // FOR UPDATE
Item findByIdForUpdate(@Param("id") Long id);

// 사용
@Transactional
public void order(Long itemId) {
    Item item = itemRepo.findByIdForUpdate(itemId);  // 최신값 + 락
    if (item.getStock() < 1) throw new SoldOutException();
    item.decreaseStock();  // 안전하게 차감
}

Gap Lock (MySQL InnoDB 전용)

행 자체가 아니라 행 사이의 빈 공간에 락 거는 것. Phantom Read 방지 목적.

현재 age 데이터: 10, 20, 30

B: SELECT * WHERE age > 20
   → (20초과~30 사이, 30 이후 공간에 Gap Lock 걸림)

A: INSERT age=25  ← 그 공간에 삽입 시도 → B 끝날 때까지 대기
A: INSERT age=35  ← 마찬가지 대기

REPEATABLE READ는 ANSI 표준상 Phantom Read 허용인데, InnoDB가 Gap Lock으로 추가 방어.
→ MySQL에서 3단계(REPEATABLE READ)로도 Phantom Read 거의 안 터지는 이유.

PostgreSQL은 Gap Lock 없고 MVCC를 더 정교하게 구현해서 다른 방식으로 처리.

7. 동시성 vs 병렬성

둘 다 동시에 실행? 아닙니다. 동시성과 병렬성! #개발자개념장착 (7분 21초)

판정 질문

개념 질문 예 →
동시성 코어가 하나뿐인 기계에서도 이 말이 성립해야 하나? 번갈아 실행. 하드웨어 조건 없음
병렬성 두 작업이 물리적으로 같은 시각에 돌아가야 하나? 코어가 둘 이상 필요

두 답이 배타적이지 않다. 멀티코어에서 도는 동시성 코드는 둘 다 「예」다.

완벽한 비유 — 요리사

100점짜리 모범 답안

  1. 동시성(Concurrency)은 논리적인 개념으로, 여러 작업을 아주 빠르게 번갈아 가며 처리해 동시에 실행되는 것처럼 보이게 하는 것.
  2. 병렬성(Parallelism)은 물리적인 개념으로, 멀티 코어에서 실제로 동시에 작업을 수행하는 것.
  3. 동시성은 여러 작업을 겹쳐 다룰 수 있도록 구성하는 구조와 설계의 개념이고, 병렬성은 멀티 코어에서 작업이 물리적으로 동시에 실행되는 상태. (동시성은 구조, 병렬성은 실행이다)

꼬리에 꼬리를 무는 질문

  1. 싱글 코어에서 동시성이 왜 필요한가요?
    • 키워드: I/O 대기, CPU 유휴, Time Slicing, 이벤트 루프 / Node.js, 인터럽트
    • I/O 대기: 디스크/네트워크 응답은 CPU 연산보다 수만~수십만 배 느림. data = read() 다음 줄은 data값 없으면 실행 불가 → 그 스레드만 멈춤(Blocked)
    • CPU 유휴: 그 대기 시간 동안 CPU가 아무것도 안 하면 자원 낭비
    • Time Slicing: CPU 시간을 잘게 쪼개서(수ms) 여러 작업에 번갈아 배정 → 유휴 시간에 딴 작업 끼워넣기
    • 이벤트 루프(Node.js): I/O 요청 던지고 결과 안 기다리고 바로 다음 코드로 진행. 결과 오면 콜백을 이벤트 큐에 넣고, 루프가 짬날 때 꺼내 실행 (블로킹 read()와 정반대 방식)
    • 인터럽트: I/O 완료를 CPU에 "알려주는" 하드웨어 신호. 폴링(계속 확인하러 감)과 반대로, 끝나면 그때 CPU 하던 일 끊고 처리 → 낭비 없이 대기 가능하게 해주는 장치
  2. 병렬성이 무조건 빠를까요?
    • 키워드: Amdahl's Law, 순차 구간, 자원 경합(Contention), Cache Coherence, 작업 분할 오버헤드, 병목(Bottleneck)
  3. 파이썬은 멀티코어 환경에서도 쓰레드 병렬 처리가 안 된다던데?
    • 키워드: GIL(Global Interpreter Lock), CPython, 프로세스 vs 스레드, multiprocessing, 동시 실행 자체를 봉쇄(자바의 synchronized와 대조)

3단계 — 캐시

[개념 정리] 캐싱은 어디서든 같은 원리

원본(느리고 크고 멂)에서 매번 안 가져오고, 자주 쓰는 걸 더 빠르고 가까운 곳에 임시 복사본으로 두는 것. 이 원리는 계층만 다를 뿐 CPU 캐시, DB 캐시, CDN/엣지 캐시 전부 동일.

계층 원본(느림) 캐시(빠름)
CPU RAM L1/L2/L3 캐시
웹/앱 Origin 서버, DB CDN 엣지 서버, Redis
  • 캐시는 항상 사본이자 임시 저장소 — 원본이 진짜 정답, 캐시는 사라지거나 만료돼도 원본에서 다시 채우면 됨 (그래서 안전하게 버릴 수 있음)
  • 캐싱 가능 기준은 "중요하냐"가 아니라 "모두에게 동일하고 자주 안 바뀌냐" — 중요한 정보(가격표)도 모두에게 같으면 캐싱 가능, 안 중요해도 개인화됐으면 캐싱 불가

[헷갈림 주의] "매체가 빠르다"(하드웨어 성질) ≠ "캐시다"(상대적 역할)

  • RAM 자체가 빠른 건 물리적 특성(재료 성질)이지 캐시 아님
  • 캐시는 절대적 속성이 아니라 비교 대상에 따라 바뀌는 상대적 역할 — 디스크 대비 RAM은 캐시(OS 페이지 캐시), CPU 캐시 대비 RAM은 원본
  • 캐시 여부 = "무엇의 복사본으로 쓰이냐"로 결정, "그 매체가 원래 빠르냐"와는 별개

[합본 영상] 캐시 계층 전략 — 브라우저부터 Redis까지

[연속재생] 성능 향상의 핵심, 캐시 완전 정복 | 브라우저 캐시 부터 Redis까지
부제: "캐시라고 다 같은 캐시가 아니다"

계층을 가까운 쪽에 둘수록 빠른 하드웨어적 근거(RAM과 HDD 사이 약 5만 배)는
«부록 — 메모리 계층과 레이턴시» 에 있다.

전체 캐시 계층 지도

사용자 ─────────────────────────────────────────────────────────────► 저장소

[Browser Cache] → [CDN] → [In-App Local Cache] → [공유 캐시(Redis)] → [DB Buffer Cache] → [Disk]
 사용자 브라우저    엣지 서버     서버 인스턴스        인스턴스 간          DBMS 자동 관리      실제 저장소
 HTTP 헤더 제어    전 세계 공유   내부 메모리          분산 환경

└──────── 애플리케이션 개발자가 설계하는 구간 ────────┘   └── DBMS/OS 소관 ──┘

요청은 가능한 한 사용자와 가까운 계층에서 끝내라.
개발자가 주로 설계하는 계층은 Browser ~ Redis — DB Buffer Cache와 Disk는 DBMS가 알아서 관리.

계층 위치 공유 범위 신선도(TTL) 제어 주체
Browser Cache 사용자 브라우저 나 혼자 (private) HTTP 헤더가 정함 서버가 헤더로 지정, 사용자가 삭제
CDN (엣지) 지역별 엣지 서버 같은 지역 사용자 전부 (public) 길게 — 안 바뀌는 데이터라서 서버가 TTL·Purge로
In-App Local Cache 서버 인스턴스 내부 메모리 그 인스턴스 안에서만 길게 — 변경 드문 데이터라서 애플리케이션 코드
공유 캐시 (Redis) 별도 캐시 서버 여러 인스턴스·사용자 공유 (public) 짧게~중간, TTL 필수 애플리케이션 코드
DB Buffer Cache DBMS 내부 DB에 붙은 세션 전체 DBMS가 판단 DBMS 자동
  • CPU 캐시(L1/L2/L3)는 이 흐름에 없지만 원리는 같음 — 원본(RAM)보다 빠르고 가까운 사본. 하드웨어가 수 나노초 단위로 자동 관리하고 개발자가 제어하지 않음
  • 네이티브 앱의 로컬 캐시는 Browser Cache 자리에 해당.
      단 HTTP 헤더가 아니라 앱이 직접 관리하고, 사용자가 앱 설정에서 지움

핵심: 캐시는 "몇 종류"로 딱 나뉘는 게 아니라, "어디 위치하냐"(계층) × "누구와 공유하고 얼마나 자주 갱신되냐"(정책) 조합으로 매번 달라지는 하나의 원리.

왜 계층 하나로는 안 되나 — 데이터마다 성질이 다르다

축 데이터마다 다른 점 그래서
변경 빈도 정적 이미지는 몇 달 안 변하고, 장바구니는 초 단위로 바뀜 빈도에 안 맞는 계층을 쓰면 낡은 데이터를 서빙하거나 캐시가 무의미해짐
공유 범위 국가 코드는 모든 사용자가 공유하고, 세션 정보는 한 사람만 씀 공유 범위에 맞는 계층이 따로 있음
용량·네트워크 비용 이미지는 수 MB, 코드 목록은 수 KB 데이터가 클수록 전송·저장 비용이 달라지고 적합한 계층도 달라짐
최신성 요구 주식 시세는 실시간이어야 하고, 공지사항은 5분 지연도 무방 허용 TTL이 계층 선택을 결정

결론: 변경 빈도 · 공유 범위 · 용량/네트워크 비용 · 최신성 — 데이터 특성에 맞는 계층을 골라야 함

① Browser Cache — 사용자 브라우저에 저장

  • 언제: CSS·JS·이미지 등 정적 리소스, 변경이 거의 없는 리소스, 사용자 재방문 시 네트워크 절감
  • 제어: ETag(변경 여부 검증 — 조건부 요청), Last-Modified(시간 기반 검증), Cache-Control(지시어별 의미는 8번 항목)
  • 강점: 서버 요청 자체가 없음 — 가장 빠름. 네트워크 비용 0
  • 주의: 개인 캐시라 다른 사용자와 공유 안 됨. 정적 리소스는 파일명 해시(versioning)로 캐시 무효화

② CDN — 전 세계 엣지 서버에 저장

  • 언제: 이미지·영상·정적 파일 전 세계 배포, 원본 서버 부하를 줄이고 싶을 때, 지리적으로 분산된 사용자 대상
  • 제어: Cache-Control(max-age·s-maxage)로 TTL 설정, Cache Purge로 콘텐츠 배포 시 무효화, CDN 콘솔/API로 직접 제어
  • 강점: 전 세계 사용자에게 빠른 응답, 원본 서버 트래픽 대폭 감소
  • 주의: Purge 없이 배포하면 구버전이 계속 서비스됨. 동적 콘텐츠 캐싱 시 개인정보 혼입 위험

③ In-App Local Cache — 서버 인스턴스 메모리에 저장

  • 언제: 변경이 드물고 조회가 매우 잦은 데이터, 국가 코드·공통 코드·설정값 등, 네트워크 왕복조차 아까울 때
  • 대표 구현: Spring Cache + Caffeine(실무 표준), Caffeine(Java — 고성능 독립 사용), Guava Cache(Java)
  • 강점: 네트워크 없음 — 인메모리 직접 접근. Redis보다 훨씬 빠름
  • 주의: 인스턴스마다 데이터가 따로 존재해 정합성 문제. 다중 서버 환경에서 업데이트 동기화 어려움

④ 공유 캐시(Redis) — 인스턴스 간 공유 캐시

  • 언제: 여러 서버 인스턴스가 동일 데이터를 공유해야 할 때, 세션·장바구니·사용자별 상태, 로컬 캐시로 해결 안 되는 다중 서버 환경
  • 제어: TTL 만료 시간 명시(필수), Eviction Policy(LRU·LFU 등), 캐시 무효화 이벤트(예: Redis Pub/Sub)
  • 강점: 모든 인스턴스가 동일 데이터 접근, 다양한 자료구조 지원
  • 주의: 네트워크 왕복 비용 발생해 로컬 캐시보다 느림. TTL 없이 쓰면 메모리 증가 → Eviction → 캐시 효율 저하

[상세] ① Browser Cache — 최신성은 어떻게 확보하나

이 구간은 슬라이드 없이 말로 진행됨

정적 리소스(CSS · JS · 이미지 · 폰트)를 사용자 브라우저의 메모리·디스크에 사본으로 두고,
다음 방문 때 네트워크 대신 그 사본을 재사용한다.
남는 문제는 사본이 낡았을 때 어떻게 알아채나 — HTTP 헤더로 처리한다.

첫 요청 — 서버가 본문과 함께 캐싱 규칙 3가지를 같이 내려준다.

규칙 헤더
캐싱해도 되나 Cache-Control: public / private / no-store
언제까지 신선한가 Cache-Control: max-age=… 또는 Expires
만료 후 재검증 수단 ETag(내용의 지문) · Last-Modified(마지막 수정 시각)

유효기간 지정은 두 방식이 있고, 둘 다 있으면 Cache-Control 이 이긴다.

Cache-Control (HTTP/1.1) Expires (HTTP/1.0)
위치 현재 표준 과거 방식 (Legacy)
지정 방식 유효기간을 초 단위 상대시간으로 만료될 절대 시각을 못 박음
예 Cache-Control: max-age=3600 Expires: Wed, 12 Feb 2026 12:00:00 GMT

절대 시각 방식은 클라이언트 시계가 틀어져 있으면 같이 틀어진다. 상대시간이 그 문제를 안 겪는 게 Cache-Control 이 표준이 된 이유 중 하나.

브라우저는 받은 사본을 메모리 캐시나 디스크 캐시에 넣는다.

어디에 넣을지는 서버가 못 정한다 — 브라우저가 판단한다. 지정하는 HTTP 헤더가 없다.
판단 근거는 리소스 크기 · 최근 사용 빈도 · 남은 RAM · 그 페이지가 아직 열려 있는지 등.
메모리 캐시는 탭이 살아 있는 동안만 유지되고 가장 빠르다. 디스크 캐시는 브라우저를 껐다 켜도 남아서, 재방문에서 실제로 쓰이는 쪽이다.

두 번째 요청 — 만료 전과 만료 후의 동작이 완전히 다르다.

같은 URL 재접속
    │
    ▼  아직 신선한가?  (첫 응답의 max-age / Expires 기준)
    │
    ├─ YES → 네트워크 요청을 아예 안 보낸다. 로컬 사본 즉시 사용
    │        (DevTools 에 "from memory cache" / "from disk cache" 로 찍힘)
    │
    └─ NO  → 조건부 요청으로 재검증한다. 본문은 아직 안 받는다
             If-None-Match: "a1b2c3"        ← 받아둔 ETag 를 되보냄
             If-Modified-Since: Mon, 01 …   ← 받아둔 Last-Modified 를 되보냄
                 │
                 ├─ 안 바뀜 → 304 Not Modified. 본문 없음.
                 │            로컬 사본 그대로 쓰고 신선도 시계만 다시 감는다
                 │
                 └─ 바뀜   → 200 OK + 새 본문 + 새 ETag. 로컬 사본 교체

304 Not Modified 는 "바뀐 걸 받아온다"가 아니라 "안 바뀌었으니 네 사본을 그대로 써라" 는 응답이다.
바뀌었으면 304 가 아니라 200 에 새 본문이 실려 온다.

서버 재검증(조건부 요청) — 두 가지 기준

"캐시 만료됐어! 근데 서버에 있는 거랑 똑같으면 304 줘!"

구분 내용 기준 (ETag) 시간 기준 (Last-Modified)
응답 헤더 ETag: "abc123" Last-Modified: [날짜]
재요청 헤더 If-None-Match: "abc123" If-Modified-Since: [날짜]

둘 다 값이 같으면 304 Not Modified(Body 없음)가 온다.
ETag 는 내용이 바뀌면 즉시 변하므로 초 단위인 시간 기준보다 정밀하다.

헤더 이름이 하는 일을 그대로 말한다 —
If-None-Match = "일치하는 게 없으면(= 바뀌었으면) 보내라"
If-Modified-Since = "그 시각 이후로 바뀌었으면 보내라"
외울 대상 아님.

[참고] HTTP 상태 코드

304 도 200 404 와 같은 것 — 서버가 응답 첫 줄에 붙이는 3자리 숫자다. 첫 자리가 부류를 정한다.

대역 뜻 자주 보는 것
1xx 정보 — 처리 중 100 Continue
2xx 성공 200 OK · 201 Created · 204 No Content
3xx 본문 대신 클라이언트가 할 일을 알려줌 301·302 리다이렉트 · 304 Not Modified
4xx 클라이언트 잘못 400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found
5xx 서버 잘못 500 Internal Server Error · 502 Bad Gateway · 503 Service Unavailable

304 가 3xx 인 게 의아할 텐데,
3xx 는 리다이렉트 전용이 아니라 "본문 안 줄 테니 뭔가 더 해라" 대역이다.
301·302 의 할 일이 "다른 URL로 다시 가라"라면,
304 의 할 일은 "네 로컬 캐시를 꺼내 써라" 다.
그래서 본문이 없고, 그 점이 전송량을 아끼는 지점이다.

401(인증 자체가 안 됨 — 로그인해라)과 403(인증은 됐는데 권한 없음)은 자주 헷갈리는 짝.

Fingerprinting (파일 지문화) — 요즘 대세의 캐시 전략

304 도 왕복 1회는 든다 — 본문만 안 올 뿐 네트워크는 탄다. 재검증을 아예 없애는 방법이 지문화다.

파일 내용의 해시를 파일명에 박아버린다.

main.js  →  main.a1b2c3.js
  • 내용이 바뀌면 해시가 바뀌므로 파일명 자체가 바뀐다
  • 파일명이 다르면 브라우저는 완전히 다른 리소스로 인식한다

그래서 갱신 방식이 재검증이 아니라 교체가 된다.
서버는 바뀐 파일을 새 이름으로 내보내고, 브라우저는 처음 보는 URL이라 그냥 새로 받는다.
캐시 만료를 기다릴 일도, 물어볼 일도 없다.

얻는 것 내용
재검증 불필요 조건부 요청 자체가 사라진다
max-age 를 1년으로 어차피 안 바뀔 파일이라 최대로 늘릴 수 있다
배포 즉시 반영 새 파일명을 참조하는 HTML만 갱신되면 끝

어떤 캐시 전략을 쓸까 — 파일 종류에 따라 갈린다

일반적인 HTML 정적 자산 (JS · CSS · IMG)
파일명 index.html 로 고정됨 Fingerprinting 적용
전략 no-cache immutable, max-age=31536000
동작 매번 재검증해서 304 또는 새 응답 서버에 묻지도 않고 100% 로컬 캐시

HTML 은 파일명을 못 바꾼다 — 사용자가 치고 들어오는 진입점이라서. 그래서 HTML만 매번 확인하고, 그 HTML이 가리키는 자산은 이름이 곧 버전이라 영구 캐싱한다.
max-age=31536000 이 1년(365일)이다.

데이터 선택 계층 이유

실수 해결
CSS를 매번 다운로드 Browser Cache 미설정 — Cache-Control 헤더 하나로 해결
모든 조회를 Redis로 변경 없는 공통 코드는 Local Cache로 충분. Redis로 보내면 네트워크 낭비

실무 캐싱 전략 3원칙

  1. 캐시는 하나가 아니다 — 브라우저 · CDN · 로컬 · 공유 캐시, 각 계층은 역할이 다르다
  2. 사용자와 가까운 계층에서 끝내라 — 사용자에게 가까울수록 빠르고, 비용이 낮고, 원본 서버 부하가 줄어든다
  3. 데이터 특성에 맞는 계층을 선택하라 — 변경 빈도 · 공유 범위 · 용량/네트워크 비용 · 최신성을 함께 고려해야 한다

8. Cache-Control

헷갈리는 캐시 설정, 쉽게 정리해 드립니다 (feat Cache-Control) (20분)

캐싱 가능 여부를 가르는 3가지 축

축 질문 HTTP 지시어
신선도(Freshness) 얼마나 자주 바뀌나, 오래 캐싱해도 되나 max-age, s-maxage (유효 초)
공유범위(Scope) 여러 사용자가 같이 써도 되나 public(공유 캐시 허용) vs private(개인 기기만)
민감도(Sensitivity) 아예 저장하면 안 되는 정보인가 no-store(캐싱 자체 금지)

조합 예시

데이터 조합 결과
가게 사진, 메뉴 public + max-age 김 CDN 상시 캐싱
좌석/재고 현황 public + max-age 짧음(초단위) 짧게 캐싱 또는 실시간 갱신
내 예약내역 private CDN 못 감, 내 기기 캐시만
결제/계좌 정보 no-store 어디에도 저장 안 함

지시어 총정리 (합본 영상에서 보충)

지시어 하는 일 갈래
public 모든 캐시(브라우저 · CDN)에 저장 허용 저장 범위
private 브라우저에만 저장 허용. 개인정보라 공유 캐시엔 못 올림 저장 범위
no-store 어디에도 저장 금지. 보안 목적 저장 범위
no-cache 저장은 하되, 쓰기 전에 항상 재검증 재검증 시점
must-revalidate 만료된 뒤에는 반드시 재검증. 만료 전엔 그냥 씀 재검증 시점
immutable 수명 동안 안 변한다고 선언. 재검증 자체를 생략 재검증 시점

no-cache 는 이름과 달리 캐싱 금지가 아니다.
저장은 하고 매번 조건부 요청으로 확인만 한다 — 안 바뀌었으면 304 라 전송량은 거의 0.
저장 자체를 막는 건 no-store 다.

no-cache 와 must-revalidate 의 차이는 만료 전 동작이다.
no-cache 는 만료 전에도 매번 묻고, must-revalidate 는 만료 전에는 안 묻는다.

지시어는 쉼표로 함께 쓴다.

Cache-Control: private, no-cache, must-revalidate

캐치테이블 예시

실전 Q&A 정리 — 인기 예약(오픈런) 시스템이 순간 트래픽 스파이크를 어떻게 버티는가

문제 상황

  • 인기 매장 예약(정오 오픈, 슬롯 소수) → 수만 명 동시 접속
  • 인터파크식 대기열 없음 — "먼저 누른 사람이 임자" 구조
  • 체감상 타이밍 승부처럼 보이지만, 이면엔 계층별 방어 설계가 있음

1. 트래픽 흡수 계층 — CDN / 엣지 캐싱 (→ 10번 Cache Miss 폭발 방어, 25번 CDN 활용과 연결)

정각에 몰리는 요청 대부분은 예약 로직과 무관한 "화면 그리는 데 필요한 데이터" (가게 사진, UI, 메뉴, 날짜 목록). 이걸 매번 origin 서버가 처리하면 예약 로직 돌기도 전에 서버가 죽음.

개념 설명
Origin 서버 진짜 로직·DB 처리하는 본서버
CDN (Content Delivery Network) 엣지 서버들을 모아놓은 전송망 서비스
엣지 서버 CDN 안의 개별 지역 서버. 콘텐츠 복사본을 들고 있다가 origin 대신 응답
캐시 히트 / 미스 엣지가 이미 들고 있으면 히트(origin 안 감), 없으면 미스(origin 한 번 조회 후 저장)
TTL (Time To Live) 캐시 유효기간. 사진·UI는 길게, "잔여석 여부"처럼 실시간성 있는 데이터는 짧게(또는 캐싱 안 함) — 안 그러면 마감된 날짜가 계속 "예약 가능"으로 보이는 오류 발생

핵심: 안 바뀌는 데이터는 CDN에서 걸러내고, origin 서버는 "예약 확정" 같은 진짜 중요한 요청만 받게 만드는 것.

데이터 종류별 캐싱 정책 (앱 전체가 하나의 스위치 아님)

데이터 캐싱 여부 이유
가게 사진, 로고, 메뉴 이미지 CDN 상시 캐싱, TTL 김 안 바뀜
가게 소개, 리뷰, 위치정보 CDN 캐싱, TTL 중간 자주 안 바뀜
날짜별 "예약 가능/마감" 상태 캐싱 안 하거나 TTL 초단위 실시간성 필요
"예약하기" 버튼 누르는 순간(재고 차감) 캐싱 절대 안 함, origin 직행 원자적 연산 필요

캐치테이블은 웹이 아니라 네이티브 앱이라 UI 골격(버튼 배치, 폰트, 아이콘)은 이미 설치 시점에 로컬에 있음. CDN이 필요한 건 그때그때 바뀌는 콘텐츠(사진·메뉴·예약현황)뿐 — 이 점이 매번 HTML/JS 받아야 하는 웹(Next.js 케이스)과 다름.

중요: 캐싱은 "트래픽 몰릴 때만 켜는 스위치"가 아니라 상시 기본 설정. 배포 시점에 헤더(Cache-Control)로 미리 정해두는 것이지, 실시간으로 온오프 안 함. 오히려 평소엔 꺼뒀다가 스파이크 순간에만 켜면 그 순간 다 같이 origin 몰려서 Cache Stampede(12번 항목) 터짐. 캐싱은 미리, 상시 걸어둬야 스파이크 순간에 이미 준비된 상태가 됨.

2. 진짜 승부처 — 원자적 연산 (재고 차감) (→ 6번 트랜잭션 격리수준, SELECT ... FOR UPDATE와 동일 원리)

슬롯 1개에 수백 명이 동시에 "확인 → 차감" 시도하면, 확인과 차감 사이 텀에 여러 요청이 끼어들어 동시에 성공 처리되는 레이스 컨디션 발생 가능. 이게 막히지 않으면 오버부킹(정원 초과 확정) 터짐.

잘못된 방식 (원자적이지 않음):
1. count = SELECT stock FROM slot WHERE id=1   ← A, B 둘 다 count=1 읽음
2. if count > 0: UPDATE stock -= 1              ← A, B 둘 다 성공 처리
→ 재고 1개인데 2명 확정 (오버부킹)

원자적 방식 (락/원자연산으로 확인+차감을 한 덩어리로):
- DB: SELECT stock FROM slot WHERE id=1 FOR UPDATE  (6번 항목의 비관적 락)
      → 다른 트랜잭션은 이 행 UPDATE 끝날 때까지 대기, 순서 보장
- 또는 Redis: DECR 커맨드나 Lua 스크립트로 "확인+차감"을 단일 원자 연산 처리

즉 캐치테이블도 겉보기엔 "먼저 누른 사람이 임자"지만, 뒤에서는 DB 락 또는 Redis 원자 연산이 순서를 강제하고 있음. 대기열 시스템(인터파크식)이 없는 대신, 이 원자적 연산 지점에서 승부가 갈림.

3. 예측 가능한 스파이크 대비 — 오토스케일 / 커넥션 풀 (→ 27번 커넥션 풀)

정오 오픈처럼 트래픽 몰리는 시각이 예측 가능하면, 실시간 트래픽보다 대응이 쉬움:

  • 오토스케일: 오픈 직전 서버 대수 미리 늘려둠
  • DB 커넥션 풀: 동시 요청 받아낼 커넥션 수 미리 넉넉히 확보 → 커넥션 부족으로 요청이 대기열에 밀리는 것 방지

"상시 방어" vs "순간 반응" — 둘 다 있음, 역할이 다름

Q. 캐싱도 상시, 원자적 연산 구조도 상시라면, 그 순간(스파이크)에만 작동하는 위기 대응 기능은 따로 없는 건가? A. 있음. 다만 캐싱/락 "구조"는 상시 존재하고, 그 위에서 실시간 부하에 따라 강도가 달라지는 반응형 계층이 따로 있음.

구분 상시 존재 (항상 켜져 있음) 순간 반응 (실시간 부하에 따라 동적으로 작동)
정체 미리 설계해둔 구조 자체 실시간 지표(요청량, 에러율, 지연시간) 보고 그때그때 반응
예시 CDN 캐싱, DB 락/원자적 연산 구조 Rate limiting 강도 조절, Circuit Breaker 트립(15번), 오토스케일 트리거, DB 커넥션 풀 대기열
비유 건물 소화 설비(항상 설치돼 있음) 화재감지기가 실제 불 감지하면 스프링클러 작동(그 순간에만 트립)

즉 "구조"는 미리 다 짜여있고 상시 대기 중이며, 그 구조 위에서 실시간 부하를 감지해 강도를 조절하는 반응형 계층(서킷브레이커, 오토스케일 트리거, 커넥션 풀 대기)이 "그 순간의 위기"를 넘기는 역할을 함. 즉석에서 뭔가 새로 만드는 게 아니라, 미리 준비된 도구를 그 순간에 꺼내 쓰는 것에 가까움.

왜 예전엔 예약 시스템에 문제가 잦았나

지금 열거한 계층들(CDN, 원자적 락, 오토스케일, 서킷브레이커)이 표준 관행으로 자리잡은 게 비교적 최근(2010년대 클라우드 대중화 이후)임. 예전엔:

원인 문제
클라우드 이전 = 고정 서버 오토스케일 자체가 불가능. 물리 서버 증설에 며칠~몇 주 걸림 → 스파이크에 서버 대수 못 늘림
캐싱 계층 미비 모든 요청이 origin/DB 직행 → DB가 병목되며 다운
원자적 락 미적용 "확인 후 차감"을 트랜잭션 없이 구현 → 레이스 컨디션으로 오버부킹 흔함
모놀리식 구조 (1~4번 항목) 예약 기능 하나 과부하돼도 전체 애플리케이션이 함께 죽음, 장애 격리 안 됨
서킷브레이커 개념 미성숙 DB가 느려지면 그 지연이 앞단까지 그대로 전파돼 연쇄 장애(20·21번 항목)

정리: 예전 실패는 "위기의 순간에 뭔가 특별한 대응을 못해서"가 아니라, 애초에 지금은 당연한 상시 구조(캐싱·원자적 락·오토스케일·서킷브레이커)들이 아직 실무 표준이 아니었거나 구축 비용이 커서 못 갖췄기 때문. 지금 시스템이 "심심하게 상시로만 돌아가는 것처럼" 보이는 이유가 바로, 예전엔 위기 때마다 즉흥 대응해야 했던 걸 지금은 미리 다 준비해놔서 위기 자체가 안 생기게 만든 것.

4. 왜 인터파크식 대기열이 없는가

뮤지컬 티켓팅은 유입 자체를 순서대로 통제(가상대기실)해야 할 만큼 트래픽 지속시간이 김. 캐치테이블은 슬롯 수 자체가 적고 승부가 몇 초~1분 안에 끝나 대기열 만들 실익이 적음 — 대신 1·2번 계층(캐싱 + 원자적 연산)으로 짧고 굵게 버팀.

캐치테이블(시간대 예약) vs 좌석 예매 — 왜 후자가 더 오래 걸리나

캐치테이블: 확인+결제가 원자적 연산 한 방(순식간) → 중간 상태 없음.

좌석 예매: 아래 이유로 한 사람이 시스템 붙잡는 시간 자체가 훨씬 김 → 순간 트래픽이 아니라 몇 분간 지속되는 트래픽이 됨 → 그래서 입장을 순서대로 흘리는 대기열이 필요해짐.

  • 좌석맵 실시간 렌더링(빈자리/선택중/팔림) + 좌석별 임시 홀드(hold) 필요 — 결제 넘어가는 몇 분간 그 좌석 남한테 안 팔리게 잠가둠(타이머 만료 시 자동 해제)
  • 동행 인원과 상의(같이 갈 자리 붙어있나), 시야 취향(가까이 vs 멀리) 비교 — 선택 자체에 고민 시간 소요, 혼자 빠르게 못 끝냄

캐치테이블의 "임시 홀드" 부재(찍으면 바로 확정)가 대기열 없이도 버틸 수 있는 핵심 이유.

용어 정리 (CDN·엣지 서버·캐시 히트/미스·TTL은 위 "1. 트래픽 흡수 계층" 표 참고, 중복 생략)

용어 뜻
Traffic (트래픽) 서버로 오가는 요청/데이터의 양·흐름. "트래픽 몰린다" = 동시 요청 수가 급증한다는 뜻
서버시간 vs 로컬시간 오차 내 기기 시계와 실제 서버 판단 시간 차이. 카운트다운은 서버 시간 기준
Rate limiting IP/기기당 요청 수 제한. 매크로 방지 겸 서버 보호
원자적 연산 "확인+차감"을 쪼개지지 않게 한 번에 처리
레이스 컨디션 동시 요청 순서가 꼬여 충돌하는 상황
오버부킹 정원 초과로 확정돼버리는 사고

흐름 요약: 정각 몰리는 트래픽 → CDN이 "구경하는 부하" 걸러냄 → 오토스케일/커넥션 풀로 몰리는 시간대 미리 대비 → 마지막 승부처인 원자적 연산(DB 락 또는 Redis)이 레이스 컨디션·오버부킹 차단.

체감 속도 차이 = "캐싱 가능한 데이터 비율" 차이

서버 성능 차이가 아니라 데이터 성격 차이. 내 포트폴리오(frontend Vercel/엣지 자동 배포, backend Railway 단일 리전)가 빠른 이유는 정적 콘텐츠 비율이 높아서. 반대로 은행(신분확인·계좌·이체)·증권(실시간 시세)이 버벅이는 이유는 캐싱 자체가 불가능한 데이터 비율이 높기 때문:

  • 개인화·보안 민감 데이터(계좌, 인증) → 캐싱 불가, 매번 origin + 다중 검증(잔액·한도·이상거래탐지) 직행
  • 실시간성 요구 데이터(주식 시세) → TTL을 극도로 짧게 잡아야 해서 캐싱 이점 거의 없음, 외부 시세 API 홉까지 추가돼 지연 누적

→ "안 바뀌는 정적 데이터 비율"이 높을수록 체감 빠르고, "캐싱 못 하는 민감·실시간 데이터 비율"이 높을수록 체감 느림.

데이터 크기와 무관한 "접근 자체의 고정 비용" 이다.

CPU 레지스터 ~0.3 ns 약 330배 빠름
L1 캐시 ~1 ns 약 100배 빠름
L2 / L3 캐시 ~4 ~ 40 ns 약 2.5 ~ 25배 빠름
메인 메모리 (RAM) ~100 ns 기준
NVMe SSD ~20 µs 약 200배 느림
SATA SSD ~100 µs 약 1,000배 느림
HDD ~5 ms 약 50,000배 느림

계층 간 크기 비교용 대표값이다. 실제 하드웨어와 접근 패턴에 따라 달라진다.
원 수치는 Peter Norvig · Jeff Dean · Colin Scott 이 정리·갱신해온 자료 기반.

1ns 를 1초라고 가정하면

나노초는 너무 작아서 감이 안 온다. 1ns = 1초 로 확대하면 격차가 체감된다.

계층 실제 레이턴시 체감 시간 (1ns = 1초 기준)
L1 캐시 ~1 ns 1초
메인 메모리 (RAM) ~100 ns 1분 40초

알아둘 점 — Random vs Sequential

위 SSD/HDD 수치는 전부 랜덤 액세스 기준이다. 순차 읽기는 전혀 다른 이야기.

랜덤 액세스 순차 읽기
접근 방식 흩어진 위치를 무작위로 접근. 매번 새 위치로 "점프" 연속된 데이터를 쭉 읽음. 한 번 접근 후 스트리밍
지배 요인 레이턴시 처리량(Throughput)
NVMe 기준 ~20 µs / 회 수 GB/s

같은 NVMe SSD라도 작은 랜덤 접근 1만 번과 큰 파일 연속 읽기는 성능이 수십 배 차이 난다.
데이터베이스 인덱스 설계가 중요한 이유가 여기 있다 — 인덱스는 랜덤 접근 횟수를 줄이는 장치다.

실무에서 자주 하는 오해

"최신 SSD 썼으니까 충분히 빠르겠지?"

NVMe SSD도 RAM보다 약 200배 느리다. "SSD로 바꿨으니 DB 성능 걱정 끝"은 위험한 접근이다.

기억할 원칙 3개.

  1. 계층 간 격차는 단위 자체가 다르다 (ns → µs → ms)
  2. 자주 쓰는 데이터는 위쪽 계층에 두는 것이 성능의 핵심
  3. 하드웨어가 발전해도 계층 간 상대적 격차는 놀랍도록 유지된다

핵심 3줄

  • 레이턴시는 데이터 크기와 무관한 접근 자체의 고정 비용이다

키워드만 던지면 감점.

레이어 기법

App / Cache Cache (Redis) · Local Cache
Database Replication(복제) · Indexing · Partitioning · 미리 계산된 결과(통계)

앞 두 레이어는 3단계 캐시의 계층 지도와 같은 얘기다.
읽기 최적화의 본체가 캐싱이라는 뜻.

쓰기(Write) 최적화 — 레이어별

레이어 기법

DB Arch Sharding · Partitioning · Eventual Consistency
DB Internal Batch Write · 인덱스 최적화

읽기가 "가까운 데서 끝내기"라면, 쓰기는 "부하를 분산하고 나중으로 미루기" 다.
큐에 넣고 응답부터 돌려주거나, 여러 샤드로 쪼개거나, 모아서 한 번에 쓴다.

성능 튜닝 전 고려사항

항목 내용
병목(Bottleneck) 찾기가 최우선 추측하지 말고 측정하라. Slow Query 등
Trade-off 고려 — 은탄환은 없다 읽기가 빨라지면 쓰기가 느려질 수 있음
Read : Write 비율 고려 대부분의 서비스는 읽기가 8:2로 압도적 → 읽기 최적화 효율이 높음

Trade-off 대표 예시

"인덱스(Index)는 읽기 성능을 높여주지만, 반대로 쓰기 성능은 떨어뜨린다."

쓸 때마다 인덱스도 같이 갱신하고 정렬해야 하기 때문.
인덱스를 늘릴수록 INSERT·UPDATE 가 비싸진다.

100점짜리 모범 답안

  1. 읽기 성능은 Web(CDN) · App(캐싱) · DB(복제/인덱싱) 계층별로 최적화한다
  2. 쓰기 성능은 App(비동기 큐) · DB(샤딩/배치 처리)를 통해 부하를 분산시킨다
  3. 무엇보다 성능 튜닝 전 병목 지점을 파악하고, 읽기/쓰기 비율에 따른 트레이드오프를 고려한다

A1. SELECT * 가 더 빨라 보이는 이유

같은 테이블을 두 방식으로 조회했을 때 생기는 시간 차를
원인일 가능성이 높은 순서로 나열한다.

① 측정 순서 — 먼저 돌린 쿼리가 하드 파싱과 물리 I/O를 다 뒤집어쓴다.
두 번째 쿼리는 데워진 캐시를 그대로 쓴다.
SELECT * 를 나중에 돌렸으면 무조건 빠르게 나온다.

순서를 바꿔 다시 재면 결과가 뒤집힌다. 이것부터 걸러낸다.

② 클라이언트가 결과를 다 안 받는다 — 툴은 그리드에 첫 50행만 채우고 멈춘다.
화면의 "완료" 는 전체 처리 시간이 아니라 첫 50행을 만든 시간이다.
ORDER BY·GROUP BY·DISTINCT 가 붙은 쪽은 결과를 전부 모아야
첫 행이 나오므로 같은 조건의 비교가 아니게 된다.

③ 컬럼을 적으면서 WHERE 절도 같이 바뀜 — 인덱스를 죽이는 건
SELECT 절이 아니라 WHERE 절에 씌운 함수다.

쓴 위치 예 인덱스
WHERE TO_CHAR(REG_DT,'YYYYMMDD') = '20260726' 못 탐
WHERE REG_DT >= TO_DATE('20260726','YYYYMMDD') 탐
SELECT SELECT TO_CHAR(REG_DT,'YYYYMMDD') 영향 없음. 행마다 CPU만 더 씀

이 표는 내장 SQL 함수(TO_CHAR 등) 기준이다.
직접 만든 PL/SQL 함수를 SELECT 절에서 부르면 얘기가 커진다 — A6.

④ 컬럼을 줄여서 플랜이 바뀜 — 조회 컬럼이 전부 인덱스 안에 들어 있으면
옵티마이저가 인덱스만 읽는 경로로 갈아탄다.
그 인덱스가 테이블만큼 크면 풀스캔보다 느려질 수 있다.

컬럼을 적었을 때 정직하게 빠른 경우

조회 컬럼이 인덱스에 다 있으면 테이블을 아예 안 간다.

SELECT USER_ID FROM USER_INFO WHERE USER_ID LIKE 'A%';
--  INDEX RANGE SCAN 만. 테이블 접근 없음

SELECT * FROM USER_INFO WHERE USER_ID LIKE 'A%';
--  INDEX RANGE SCAN + TABLE ACCESS BY INDEX ROWID
--  건마다 테이블 블록을 랜덤으로 한 번씩 더 읽음

실행계획에 TABLE ACCESS BY INDEX ROWID 줄이 있느냐로 갈린다.
건수가 많을수록 차이가 벌어진다.

성능과 별개로 컬럼을 적는 이유가 하나 더 있다.
테이블에 컬럼이 추가되면 SELECT * 는 결과 컬럼 순서가 밀려
ResultSet 인덱스 접근과 resultMap 매핑이 조용히 깨진다.

A2. 파싱과 커서 공유

오라클은 SQL 텍스트를 받으면 공유 풀의 라이브러리 캐시에서
같은 텍스트를 찾고, 있으면 저장된 실행계획을 그대로 쓴다.
이 재사용 판정을 커서 공유(cursor sharing) 라 한다.

이름 무슨 일이 일어나나 비용
소프트 파싱 캐시에서 실행계획을 찾아 재사용 쌈
하드 파싱 옵티마이저가 통계를 읽고 플랜을 새로 계산 비쌈

하드 파싱은 조인 순서와 접근 방법 조합을 전부 따져 비용을 매긴다.
CPU를 많이 쓰고 라이브러리 캐시에 래치를 잡아 다른 세션과 경합한다.

같은 SQL 판정은 텍스트가 바이트 단위로 같아야 한다.
대소문자·공백·주석이 하나만 달라도 다른 SQL로 친다.

SELECT * FROM USER_INFO WHERE USER_ID = '1234'   -- 값마다 새 SQL, 매번 하드 파싱
SELECT * FROM USER_INFO WHERE USER_ID = :1       -- 최초 1회만 하드 파싱

MyBatis에서 갈리는 지점

작성 오라클이 보는 텍스트 커서
#{userId} ... WHERE USER_ID = :1 하나 1개를 계속 재사용
${userId} 값마다 다른 텍스트 값 종류만큼 생성

로그에 USER_ID = 1 로 찍히는 건 MyBatis가 읽기 좋으라고
파라미터를 끼워 보여주는 것이다. V$SQL.SQL_TEXT 에는 :1 로 들어 있다.

리터럴 SQL을 남발하면 1회용 커서가 공유 풀을 채워
재사용될 커서를 밀어낸다. 이걸 라이브러리 캐시 오염이라 한다.

CURSOR_SHARING 파라미터를 FORCE 로 두면 오라클이 리터럴을
바인드 변수로 자동 치환한다. 소스를 못 고치는 레거시에 쓰는 응급처치고,
플랜 품질이 떨어질 수 있어 기본값은 EXACT 다.

A5. 옵티마이저 — 학습이 아니라 통계 계산

기본 동작은 학습이 아니라 매번 계산이다.

1. 통계정보를 읽는다       → 이 조건이면 몇 건 나오겠다 (카디널리티 추정)
2. 후보 경로마다 비용 계산  → 인덱스로 가면 블록 몇 개, 풀스캔이면 몇 개
3. 제일 싼 경로를 고른다

전부 1번에 달렸다. 여기가 틀리면 2·3은 자동으로 틀린다.
통계는 DBMS_STATS 가 수집해 딕셔너리에 저장한 값이고,
실시간 값이 아니라 수집 시점에 찍은 사진이다.

통계 어디에 무엇
NUM_ROWS·BLOCKS ALL_TABLES 테이블 규모
고유값 수·히스토그램 ALL_TAB_COL_STATISTICS 컬럼 값 분포
CLUSTERING_FACTOR ALL_INDEXES 인덱스 효율

인덱스가 오히려 느린 경우

인덱스는 건마다 랜덤 액세스, 풀스캔은 한 번에 여러 블록을 순차로 읽는다.
결과가 전체의 대략 5~15%를 넘어가면 풀스캔이 이긴다.

CLUSTERING_FACTOR 는 인덱스 정렬 순서와 테이블의 물리 저장 순서가
얼마나 어긋나 있는지를 나타낸다.

값 의미
BLOCKS 에 가까움 좋음. 인덱스 순서대로 읽으면 같은 블록이 연달아 나옴
NUM_ROWS 에 가까움 나쁨. 건마다 다른 블록이라 랜덤 I/O가 됨

통계가 어긋나는 흔한 이유

  • 오래됨 — 배치로 100만 건 넣었는데 통계는 1만 건 시절 값
  • 편중 분포인데 히스토그램이 없음 — Y 99% / N 1% 를 균등으로 가정
  • 조건 간 상관관계 무시 —
    시도='서울' AND 구='강남구' 를 독립으로 보고 확률을 곱해 실제보다 적게 추정

현장에서 "옵티마이저 문제" 라는 말은 대개
"통계가 실제와 어긋났다" 를 가리킨다.

예외적으로 보정이 도는 기능들

기능 도입 하는 일
바인드 피킹 9i 하드 파싱 때 첫 바인드 값을 엿보고 그 값 기준으로 플랜을 짬
적응형 커서 공유 11g 값 범위별로 자식 커서를 나눠 각각 다른 플랜을 씀
통계 피드백 11.2 예상과 실제 행수가 크게 벌어지면 다음 실행 때 보정
SQL 계획 관리 11g 검증 안 된 새 플랜을 못 쓰게 막음

트리거는 실행 횟수가 아니라 예상과 실제가 어긋난 정도다.
실행 횟수는 캐시에서 안 밀려나는 우선순위에만 영향을 준다.

바인드 피킹이 만드는 증상

STATUS 가 Y 99만 건 / N 100건인 테이블에서

1회차  STATUS='N' 실행  → 100건 예상, 인덱스 플랜 생성. 빠름
2회차  STATUS='Y' 실행  → 같은 플랜 재사용. 99만 건을 인덱스로 → 느림

"어제는 빨랐는데 오늘 느리다", "재기동하니 반대가 됐다" 의 정체다.
같은 SQL의 자식 커서가 여러 개 생겼는지로 확인한다.

     , IS_BIND_SENSITIVE, IS_BIND_AWARE

WHERE  SQL_TEXT LIKE '%USER_INFO%'
  AND  SQL_TEXT NOT LIKE '%V$SQL%'
ORDER BY SQL_ID, CHILD_NUMBER;

CHILD_NUMBER 가 여러 개인데 PLAN_HASH_VALUE 가 서로 다르면
같은 SQL인데 플랜이 갈렸다는 뜻이다.

A6. PL/SQL 함수 호출 비용 — SQL과 PL/SQL 사이 컨텍스트 스위칭

함수 안에 자기 SELECT 문이 있으면 A1의 표로는 설명이 안 된다.
오라클은 SQL 엔진에서 PL/SQL 엔진으로 넘어갔다가, 그 안에서
다시 SQL 엔진을 불러 값을 받고, PL/SQL로 돌아와 결과를 만들어
SQL 엔진에 되돌려준다. 이 왕복을 컨텍스트 스위칭이라 한다.

한 번의 전환은 마이크로초 단위라 눈에 안 띈다. 문제는 곱셈이다.

1만 행 × SELECT절 함수 6번 = 컨텍스트 스위칭 6만 회

SELECT * 로 바꿔서 빨라졌다면 인덱스도 캐시도 아니라
이 함수 호출 자체가 빠진 것부터 의심한다.

확인 순서

  1. 의심 가는 함수 소스에 SELECT 문이 있는지 본다 —
    toolbox/tools/sql_snippets.html 의 프로시저/함수 소스 조회(USER_SOURCE)로 바로 확인된다
  2. 그 컬럼만 빼고 같은 조건으로 다시 돌려 시간 차를 잰다 —
    차이가 크면 함수가 원인으로 확정된다
  3. V$SQL 로 실제 ELAPSED_TIME 을 봐서 체감이 아니라 수치로 남긴다

고치는 법 — 두 갈래

방법 하는 일 언제
RESULT_CACHE 같은 인자로 다시 부르면 함수를 안 태우고 캐시값을 바로 돌려줌 인자 조합이 적고 자주 겹칠 때 (공통코드 → 명칭 변환 등)
JOIN 으로 대체 함수가 하던 조회를 쿼리 안에 직접 붙여 컨텍스트 전환 자체를 없앰 함수 내부가 단순 조회 하나뿐일 때. 여러 곳을 고쳐야 해서 손은 더 감 
CREATE OR REPLACE FUNCTION FC_UCM_CMM_CDVL_NM_INQ(
  p_grp_cd IN VARCHAR2, p_cd IN VARCHAR2
) RETURN VARCHAR2
RESULT_CACHE
IS
  v_nm VARCHAR2(200);
BEGIN
  SELECT CDVL_NM INTO v_nm FROM CMM_CDVL WHERE GRP_CD = p_grp_cd AND CD = p_cd;
  RETURN v_nm;
END;

RESULT_CACHE 는 세션이 아니라 인스턴스 전역에 캐시한다.
값이 자주 안 바뀌는 공통코드·룩업성 함수에 맞는다.
원본 테이블이 바뀌면 관련 캐시는 자동으로 무효화된다.

원인이 함수 호출이면 EXPLAIN PLAN 은 처음부터 못 잡는다 — A7.
플랜엔 테이블 접근 스텝만 나오고, SELECT절을 계산하며
PL/SQL을 몇 번 들락거리는지는 플랜에 남지 않는다.

A7. 무엇으로 재나 — EXPLAIN PLAN의 한계

EXPLAIN PLAN 은 쿼리를 실행하지 않는다.
옵티마이저에게 "이걸 돌린다면 어떻게 할 건가" 를 묻고 답만 받아 적는다.

돌려 보면 이렇게 나온다

두 문장이다. 첫 문장이 플랜을 PLAN_TABLE 에 적고,
둘째 문장이 그것을 꺼내 표로 그린다.

EXPLAIN PLAN FOR
SELECT USER_ID, USER_NM, DEPT_CD
FROM   USER_INFO
WHERE  USER_ID = 'USER001';

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

볼 것 뜻

Cost 2 → 214, Rows 1 → 4,821.

  • 인덱스를 타는지 — TABLE ACCESS FULL 이 보이면 거기서 끝난다
  • 조인 방식과 순서
  • 쿼리를 고치기 전후의 구조 비교
  • 실행을 안 하니 10시간짜리 쿼리도 즉시 답이 나온다

못 하는 것

한계 내용

시간·블록 없음 어느 단계에서 시간을 태웠는지 안 나옴
적응형 플랜 12c 이후 실행 중에 바뀌는 플랜은 바뀌기 전 모습만 보여줌

DBMS_XPLAN.DISPLAY_CURSOR 는 반대로 실제 돌린 커서를 캐시에서 꺼내 본다.
A-Rows(실제 행수), Buffers(읽은 블록), A-Time(실제 시간)이 찍힌다.
E-Rows 와 A-Rows 가 크게 벌어지면 통계가 어긋났다는 신호다.

DB가 느린지 앱이 느린지를 구분하지 못한다.
로그 시간이 V$SQL 시간보다 훨씬 크면 범인은 DB 밖에 있다.

운영에서는 테스트하지 말고 결과만 회수한다

SELECT 라도 운영에서 함부로 돌리면 이런 일이 생긴다.

  • 큰 풀스캔 한 번이 버퍼 캐시를 밀어내 이후 모든 화면이 느려진다
  • 정렬이 크면 TEMP를 잠식해 다른 세션이 ORA-01652 로 죽는다
  • 툴에서 리터럴로 친 SQL이 공유 풀에 쌓여 운영 커서를 밀어낸다

실행은 운영 화면이 이미 하고 있으니 흔적만 꺼내 보면 된다.

-- 운영에서 실제로 돈 커서 찾기
SELECT SQL_ID, CHILD_NUMBER, PLAN_HASH_VALUE, EXECUTIONS
     , ROUND(ELAPSED_TIME/EXECUTIONS/1000, 2) AS AVG_MS
     , ROUND(BUFFER_GETS/EXECUTIONS)          AS GETS_PER_EXEC
     , ROUND(DISK_READS /EXECUTIONS)          AS READS_PER_EXEC
FROM   V$SQL
WHERE  SQL_TEXT LIKE '%USER_INFO%'
  AND  SQL_TEXT NOT LIKE '%V$SQL%'
ORDER BY LAST_ACTIVE_TIME DESC;

-- 그 커서가 실제로 쓴 플랜
SELECT * FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR('찾은SQL_ID', 자식번호, 'ALLSTATS LAST')
);

운영은 보통 STATISTICS_LEVEL 이 TYPICAL 이라 A-Rows·A-Time 칸이 빈다.
플랜 구조와 E-Rows, V$SQL 의 블록 수치는 그대로 나오므로
플랜이 갈렸는지 비교하는 데는 충분하다.

툴에서 조건을 맞추는 법

VARIABLE v_user_id VARCHAR2(20)
EXEC :v_user_id := 'USER001';

SET AUTOTRACE TRACEONLY   -- 결과는 안 뿌리고 전체 fetch + 통계만
SET TIMING ON

SELECT /*+ GATHER_PLAN_STATISTICS */ *
FROM   USER_INFO
WHERE  USER_ID = :v_user_id;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

바인드 변수를 실제로 써서 운영과 같은 SQL 텍스트를 만들고,
3회 이상 돌려 2회차 이후 값만 쓴다. 1회차는 파싱과 물리 I/O가 섞여 있다.

ALTER SYSTEM FLUSH BUFFER_CACHE 로 조건을 맞추는 방법도 있지만
인스턴스 전체의 캐시를 날려 모든 세션이 느려진다.
개발·테스트 인스턴스 한정이고 운영에서는 쓰지 않는다.

  1. EXPLAIN PLAN 으로 구조 확인 — 대부분 여기서 끝난다
  2. V$SQL 로 실제 실행 횟수·시간·플랜 해시 확인
  3. DISPLAY_CURSOR 로 단계별 실측
  4. 그래도 모르면 SQL Monitor — 라이선스 확인 필요

A8. 옵티마이저 힌트

/*+ ... */ 를 옵티마이저 힌트라 한다. 문법 조건이 까다롭다.

  • /* */ 는 일반 주석이고 + 가 붙은 /*+ */ 만 힌트로 읽는다
  • + 는 여는 /* 에 붙어야 한다. /* + INDEX... 는 그냥 주석이 된다
  • SELECT·INSERT·UPDATE·DELETE 키워드 바로 뒤에만 유효하다
  • 틀린 힌트는 에러 없이 조용히 무시된다. 인덱스명에 오타가 나도 아무 말 없이 풀스캔으로 돈다

경로를 바꾸는 힌트

힌트 하는 일
INDEX(A IDX_01) 지정한 인덱스를 쓰게 함
FULL(A) 풀스캔을 쓰게 함
LEADING(A B) 조인 순서를 지정
USE_NL(B) 중첩 루프 조인을 쓰게 함
FIRST_ROWS(10) 첫 10행이 빨리 나오도록 최적화
PARALLEL(A, 4) 병렬로 처리

계측만 켜는 힌트

GATHER_PLAN_STATISTICS 는 경로를 바꾸지 않는다.
이번 실행의 단계별 실제 행수와 시간을 재서 남기라는 스위치다.
세션에 STATISTICS_LEVEL = ALL 을 거는 것과 같은 일을 쿼리 하나에만 적용한다.
붙이지 않으면 DISPLAY_CURSOR 의 A-Rows 칸이 빈다.
